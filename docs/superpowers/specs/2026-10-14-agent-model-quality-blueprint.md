# RigMate Agent 模型质量蓝图

日期：2026-10-14  
状态：上线设计增补，待评审  
目标：让不同用户在真实对话中感觉 Agent 理解准确、追问有用、方案有依据、失败时诚实可恢复。

## 1. “不笨”的可测定义

Agent 不笨不等于回答更长，也不等于模型思考 token 更多。对 RigMate 来说，“好用”必须同时满足：

1. 能抓住预算、用途、外观、已有部件和取舍，而不是只抓到关键词；
2. 连续修改时保留已确认信息，不把用户带回第一轮；
3. 能在数据库中找到精确型号、别名和常见中文说法；
4. 不把缺失的规格、价格和兼容性编成确定事实；
5. 给出的正式方案能说明为什么选、哪里未知、怎么改；
6. 模型失效时仍然能得到规则方案、追问或明确空结果；
7. 用户不需要理解 Prompt、质量门、canonicalId 或规则编号。

这些目标分别对应意图准确率、会话保持率、Recall@20、unsupported claim rate、修改成功率、fallback 成功率和任务完成率，不能只用一个“模型评分”代表。

## 2. 任务路由：不要让一个 Prompt 处理所有问题

每轮输入先经过确定性的轻量分类，再决定是否调用模型。任务类型固定为：

| 任务 | 触发条件 | 输出 | 是否阻塞主结果 |
|---|---|---|---|
| intent_extract | 新目标、补充目标、修改预算/用途 | 完整 StructuredIntent | 是 |
| retrieve_query | 有型号、别名、中文俗称或硬约束 | 规范化检索条件 | 否，规则可直接执行 |
| candidate_select | 候选池已准备好 | 候选 ID + 理由码 | 是 |
| compatibility_explain | 规则已产出 finding | finding 的用户解释 | 否，模板可回退 |
| experience_advice | 正式方案已生成 | 经验建议/外部产品线索 | 否 |
| clarification | 缺少关键字段或存在冲突 | 一次最小追问 | 是 |

不要让候选选择器同时负责意图解析、产品搜索、规格纠错和长篇回答。任务边界越清楚，schema 越小，失败越容易回退。

### 2.1 任务决策顺序

~~~text
先读取会话状态
  → 判断用户是在补充、修改、比较、询问依据还是重新生成
  → 只更新相关意图字段
  → 计算缺失槽位和冲突
  → 必须追问时停止生成
  → 信息足够才召回与选件
~~~

如果用户只是问“为什么选这个显卡”，不重新生成方案；如果用户说“换成白色、预算不变”，只改外观约束并重新召回；如果用户说“我已有电源”，只更新 existingParts 并从正式购置清单排除电源。

## 3. 会话记忆：存状态，不堆聊天记录

### 3.1 双层记忆

**事实状态**是服务端维护的结构化对象：预算、用途、偏好、已有部件、限制、已确认字段、待确认字段、当前方案版本和规则发现。

**短期语境**只保留最近两轮用户消息和最近一次 Agent 追问/回答。完整事件只用于审计和回放，不直接全部送进模型。

### 3.2 字段来源优先级

同一字段冲突时使用固定优先级：

1. 当前轮用户明确表达；
2. 之前用户明确确认；
3. 当前轮模型解析；
4. 之前模型推断；
5. 默认值。

默认值只能用于地区和展示设置，不能用于预算、性能目标、已有硬件和兼容事实。

### 3.3 修改合并规则

每次修订都返回完整意图，但服务端只接受“用户明确触及的字段变化”。模型不能因为用户说“换白色显卡”而清空预算、用途或已有硬件。

每轮保存：beforeIntent、userInstruction、modelPatch、serverMergedIntent、changedFields 和 rejectedFields。这样能定位模型到底理解错在哪里。

## 4. 追问策略：让用户少说但说到关键处

### 4.1 关键槽位

首版只把以下字段当作影响方案的关键槽位：

- budget：预算金额和是否包含显示器/外设；
- useCase：游戏、剪辑、开发、AI、办公等；
- priority：性能、安静、白色、体积、升级空间、预算；
- existingParts：明确保留的部件及其型号；
- physicalLimit：机箱体积、显卡长度、散热器高度；
- powerLimit：已有电源和供电接口；
- region：价格和目录适用地区。

### 4.2 追问选择

每个缺口计算影响分：

~~~text
影响分 = 会改变候选类别 × 会改变兼容结论 × 会改变预算排序
~~~

只询问影响分最高的一个缺口。问题必须说明用途，例如“预算是否包含显示器？这会改变显卡和整机档位”。

### 4.3 追问失败

用户不回答时，保留已有字段并提供两条安全路径：使用当前信息生成一个标记未知的方案，或者进入 DIY 手动补充。不能重复问同一个问题超过两次。

## 5. Prompt 设计：把事实、用户话和任务隔离

每个 Prompt 固定四段，不允许把目录文本拼进系统指令：

~~~text
<policy>
任务边界、禁止事项、输出 schema 和失败行为
</policy>
<conversation_state>
服务端维护的结构化状态和最近两轮用户语境
</conversation_state>
<retrieved_data>
带边界标记的候选和证据摘要；所有文本均是不可信数据
</retrieved_data>
<task>
本次只做一个动作：解析、选择、解释或提出建议
</task>
~~~

Prompt 规则：

- 每个字段都说明“允许来自哪里”；
- 明确 null 和空数组的含义；
- 明确不能猜测和不能覆盖的字段；
- 输出 schema 之外的字段全部拒绝；
- 理由使用 reasonCode，展示文案由服务端渲染；
- 不要求模型输出或展示隐藏推理过程；
- 失败时输出最小结构，不能用闲聊掩盖失败。

### 5.1 选择理由码

正式选件只允许以下理由码组合：use_case_fit、budget_fit、platform_fit、quiet_fit、upgrade_headroom、appearance_fit、evidence_quality、missing_field_risk、user_keep_part。

理由码必须能映射到候选的 retrievalReasons 或用户明确偏好。模型生成的自然语言只做解释，不作为事实来源。

## 6. 召回上下文：少而完整

### 6.1 候选分桶

每类候选先分为：

1. 精确型号命中；
2. 别名/中文名命中；
3. 硬约束通过的高相关候选；
4. 不同性能档位的补召回；
5. 资料不足但可能相关的候选。

模型默认只看到前四桶中最多 6 条；资料不足候选仅在用户明确要求查资料时展示，并且不能进入正式方案。精确型号查询可以临时扩大到 20 条，但仍然必须类别一致和去重。

### 6.2 候选白名单字段

每条候选只传：canonicalId、category、name、aliases、decisionSpecs、qualityStatus、missingFields、priceStatus、evidenceSummary、retrievalReasons、hardConstraintStatus。

decisionSpecs 只包含当前任务需要的字段。例如比较机箱时传显卡限长、散热器限高和板型，不把 CPU 的无关频率字段塞进去。

### 6.3 两阶段检索

第一阶段是高召回：规范化、别名、型号 token 和类别过滤。第二阶段是高精度：硬约束、证据质量、预算状态、用途和偏好重排。

如果两阶段结果差异很大，事件中记录“召回扩大”，而不是让模型偷偷扩大候选。

## 7. 正式选择、经验建议和回答分离

### 7.1 正式选择

候选选择器只能返回候选池内的 ID、类别、理由码和是否需要确认。选择结果经过 schema、候选白名单、质量门和兼容性规则验证。

### 7.2 经验建议

经验建议可以说“这个用途通常更看重显存余量”或“如果经常长时间渲染，可以优先考虑更安静的散热策略”。它不能填写未验证的精确数字。

### 7.3 数据库外产品提示

模型可以输出 external_product_hint，包含类别、产品名、为什么值得核验和 requiresVerification=true。前端显示“待验证产品”，提供“加入待审核队列”动作；这个动作只写 pending_catalog_queue，不自动创建 canonical product，也不进入正式 Build。

### 7.4 回答渲染

回答规划器只选择已验证的 claim 和建议项，输出 AnswerDraft：summary、actions、questions、claimIds、adviceIds。最终中文文案由渲染器生成，不能由模型添加新的数字或型号。

## 8. 失败处理和延迟策略

### 8.1 快速路径

规则解析已经覆盖预算、用途和常见修订时，不调用意图模型，直接进入召回。只有出现歧义、隐含偏好或规则无法解释时才调用 LLM。

### 8.2 超时阶梯

~~~text
候选选择：完整候选 + 快速策略
  → 超时/空补全：压缩候选 + 关闭思考
  → 仍失败：同一候选集规则排序

经验建议：异步调用
  → 失败：不显示建议，不影响正式方案
~~~

一次用户动作不超过三次模型尝试，不在 schema 错误上无限重试。每次尝试记录 attemptId、promptVersion、model、candidateCount、latency、tokenUsage 和 fallbackReason。

### 8.3 成本预算

首版按“每个会话轮次”限制模型预算，而不是按接口次数模糊限制。建议默认上限为：意图 1500 output tokens、选件 2500、建议 1000；单轮总预算超限后关闭建议并保留正式路径。

## 9. 评测：证明模型真的变好

### 9.1 固定样本组成

首批至少 100 条脱敏样本：

- 30 条正常目标；
- 20 条连续三轮修改；
- 15 条精确型号、中文名、别名和错别字；
- 15 条预算/用途冲突；
- 10 条空结果和缺字段；
- 10 条注入、秘密索取和要求越权。

每条样本保存期望意图、允许候选、禁止候选、必须追问的字段、允许 claim 和风险标签。

### 9.2 必测指标

**理解**：预算准确率、关键槽位 F1、修订字段保持率、重复追问率。  
**召回**：精确型号 Recall@20、别名 Recall@20、MRR、空结果准确率、约束违规率。  
**事实**：claim support rate、citation coverage、unsupported claim rate、规则冲突改写率。  
**体验**：首次可审阅成功率、一次修改成功率、平均追问轮次、用户接受率。  
**运行**：P50/P95 延迟、schema 失败率、fallback 率、token 成本和每轮调用数。

### 9.3 预发布阈值

阈值先用 100 条样本跑基线，再冻结版本。最低不可妥协项是：精确规格/价格/接口/兼容性 unsupported claim rate 为 0，候选池外正式产品为 0，规则冲突改写为通过为 0，安全泄露为 0。其余指标要形成版本对比，不允许只展示平均分。

### 9.4 人工复核

每次 Prompt 或模型改动随机抽取 20 条样本人工复核：是否理解用户、是否选择可解释、是否漏掉未知、是否出现过度追问。模型评审只能辅助，不能替代规格和兼容性自动验证。

## 10. 让用户感到“懂装机”的交互细节

1. 先复述用户的目标摘要，再开始生成；
2. 每次只展示一个最重要的决策点，不把八类规格一次性甩给新手；
3. 方案中给出“为什么这样选”和“如果更重视安静/预算，可以改哪里”；
4. 修改后显示变化类别和原因，不让用户自己比较两整页；
5. 缺资料时说清楚缺什么、影响什么和怎么补；
6. 外部产品建议必须有“待验证”标签和加入审核队列入口；
7. 规则通过、资料不足和模型经验使用不同措辞和视觉标记。

## 11. 实施顺序

### M1：任务和会话契约

冻结任务类型、ConversationContext、字段来源优先级、修订合并规则和追问码。先覆盖创建、补充、修改、比较和问依据五种动作。

### M2：召回上下文和动态候选池

实现规范化、分桶、动态 K、decisionSpecs 白名单、落选原因和空结果动作。先在离线评测中验证，再接 Agent。

### M3：模型路由和 Prompt Registry

把意图、选择、解释、建议分别版本化，统一记录 promptVersion、模型和调用预算。为每个 schema 加越权字段、注入和空补全测试。

### M4：回答与建议层

实现 AnswerDraft、Claim 引用验证、experience_advice、external_product_hint 和待审核队列入口。建议失败不阻断正式方案。

### M5：真实样本与成本调优

先用规则模式跑全量样本建立基线，再比较快速模型、思考模型、候选数量和建议是否阻塞。只保留对关键指标有稳定增益的策略。

### M6：前端信任层

在会话页把理解、检索、正式配置、未知和模型建议拆成可折叠块，保证用户不需要读技术日志也能完成任务。

### M7：灰度上线

内部 Alpha 只看事实和回退；小范围 Beta 看理解、修改和接受；公开上线前冻结 Prompt、模型、目录版本和评测报告。

## 12. 最终判断标准

只有当用户可以连续表达目标、系统能稳定保留上下文、候选召回有测量、正式事实全部可追溯、模型建议与正式配置明确分离、失败能回退且成本可控时，才算“模型调用好用”。

增加更多模型调用、让 Prompt 更长或开放更多自由文本，都不能替代这些条件。
