# RigMate 系统布局规划 v2（UI 总纲）

> **本文档是 UI 结构层单一事实来源**：先改本文档，再动页面结构与交互代码。
> 视觉事实源见 `00-visual-system.md` 与 `boards/`；本文档决定页面职责、产品对象和信息披露层级。
> 2026-09-23 重校准：RigMate 从“逐项录入后检查兼容”调整为“表达目标后自动生成方案，再按需 DIY”。

## 0. 产品定位

**RigMate 是面向 PC 装机与升级决策的 Agent 工作台。**

用户可以直接说：

> “我想配置一台 2 万预算的白色海景房主机，主要做剪辑和打游戏。”

系统负责理解目标、检索硬件资料、生成一套可编辑方案、自动检查主要风险，并在真正需要用户判断时提问。用户不需要先填写 CPU、主板、显卡等八类字段。

RigMate 不是聊天壳，也不是电商导购。它由一个装机助手持续编排多个受约束能力：目标理解、硬件检索、方案生成、兼容校验、替代建议和报告整理。

## 1. 用户主流程

```text
表达目标 → 自动生成方案 → 自动校验 → 方案审阅 → 接受 / 修改 / 自由 DIY → 保存与导出
```

两条入口共用同一份方案状态：

- **从目标开始**：自然语言、预算、用途、风格和已有硬件；适合大多数用户。
- **从清单开始**：粘贴已有配置单、商品标题或链接；系统自动识别并生成可编辑草稿。
- **自由 DIY**：经验用户直接进入高级编辑，修改后仍由系统自动重算预算与风险。

“兼容检查”不再是用户必须主动点击的主步骤，而是每次生成或修改后的后台护栏。只有出现冲突、未知或取舍时，才把决策呈现给用户。

## 2. 信息架构

| 导航区 | 路由 | 角色 | 默认体验 |
|---|---|---|---|
| **开始配置** | `/` | 目标输入与最近方案 | 一句话目标输入，少量可选约束，继续最近方案 |
| **我的方案** | `/projects` | 方案生命周期 | 生成中、待确认、可继续 DIY、已完成、已归档 |
| **方案工作台** | `/design/[id]` | 目标、Agent 活动、方案审阅和调整 | 方案结果是主视觉，Agent 活动是辅助信息 |
| **硬件资料** | `/hardware` | 高级用户查看目录和来源 | 非普通用户必经流程 |
| **证据资料** | `/evidence` | 价格和规格证据 | 按需展开，不压在首屏 |
| **高级 DIY** | `/diy` | 逐项编辑、精确规格和规则详情 | 保留现有八类硬件表单能力，作为进阶工作区 |

导航壳保持轻量：品牌、开始配置、我的方案，以及资料/高级入口。Agent 不单独做成一个聊天页面，而是贯穿目标入口和方案工作台。

## 3. 页面契约

### 3.1 开始配置 `/`

首屏只回答一个问题：**“你想配置一台什么样的电脑？”**

核心内容：

- 大面积自然语言输入；
- 预算、用途、外观、地区、显示器是否包含、已有硬件等少量可选约束；
- 最近方案和继续编辑入口；
- “从目标开始”“从已有清单开始”“进入自由 DIY”三个明确动作。

示例只能作为 placeholder，不写入真实表单。首屏不展示八类字段、规则数量、数据库状态、导入 commit 或许可证说明。

### 3.2 方案工作台 `/design/[id]`

页面由“结果区 + 活动区 + 按需细节”组成：

- 顶部：目标摘要、预算、方案版本、当前状态；
- 主区：方案摘要、核心硬件、预算区间、用途适配、外观一致性、关键取舍；
- 活动区：正在理解、检索、生成、校验、等待确认的短事件；
- 决策区：只展示需要用户选择的动作，例如“换更安静的显卡”“保留 2 万预算”“我已有 850W 电源”；
- 依据抽屉：规格来源、价格日期、兼容性细节和未知项默认折叠；
- 操作：接受这一版、继续调整、进入高级 DIY、导出方案。

不做无依据的总分。可以展示“适合剪辑”“适合 2K 游戏”“白色风格一致”等结论，但每条结论都要能回到用户目标、目录事实、价格证据或明确标注的经验判断。

### 3.3 方案库 `/projects`

方案列表按生命周期分组：

- 生成中；
- 待确认；
- 可继续 DIY；
- 已有检查结果；
- 已归档。

“从自然语言开始”和“粘贴配置单”是创建入口，不把复核表单长期堆在列表下方。

### 3.4 高级 DIY `/diy`

复用现有逐项编辑能力，但将规则细节、字段完整度、目录来源和检查历史放入渐进式展开区。修改后自动触发校验并在触发位置附近反馈，不要求用户手动寻找底部消息。

### 3.5 硬件与证据 `/hardware`、`/evidence`

它们是资料支撑页面，不是普通用户的起点。方案详情可按需链接到某一条目录事实或价格证据。

## 4. Agent 产品边界

只有一个装机助手，内部按技能调用工具：

- 理解目标：预算、用途、风格、性能优先级、已有硬件和排除项；
- 检索硬件：目录、别名、规格来源和可比价格证据；
- 生成方案：组合候选并解释取舍；
- 自动校验：调用确定性兼容性规则；
- 持续调整：理解“换白色显卡”“安静一点”“我已有电源”等修改；
- 整理产物：方案、待确认事项、证据摘要和报告。

事实边界：

1. 精确规格、尺寸、接口、价格和兼容性优先来自目录、来源记录、用户输入和规则工具。
2. 模型可以用经验完成用途理解、审美组合和取舍建议，但经验建议必须标注为经验或待核实。
3. 模型不直接写入正式项目，不绕过校验，不把未知包装成通过。
4. 用户接受方案后才生成正式 `Build`；模型生成中的候选属于方案草稿。
5. 规则编号和完整字段默认隐藏，用户通过“查看依据”才展开。

## 5. 视觉与信息披露

继续使用 **仪器白 / 技术规格单**：暖白、墨黑、发丝线、单一仪器橙、等宽数字和克制动效。

新页面增加呼吸感和结果层级：

- 方案结果是主视觉，不是输入表格；
- Agent 事件使用短句、时间戳和状态，不写长篇系统说明；
- 预算和方案版本是主要数据；
- 兼容性、证据、规则细节进入抽屉或展开层；
- 不使用深色发光、玻璃拟态、紫色渐变、圆角卡片墙或多 Agent 角色营销。

## 6. 迁移路径

1. **M27：规格重校准**：更新业务规格、架构决策、UI 总纲和视觉母版。
2. **M28：共享契约与草稿数据层**：增加设计请求、方案草稿、方案条目、Agent 运行和事件模型，保留现有 Build 数据。
3. **M29：目标入口垂直切片**：不用真实模型也能完成目标输入、方案生成、自动校验、审阅和接受。
4. **M30：可插拔 LLM/RAG**：结构化输出、检索上下文、超时、降级和审计。
5. **M31：持续调整**：自然语言修改方案，自动重算并保留版本。
6. **M32：高级 DIY**：经验用户在同一方案中自由替换硬件，自动重算风险和预算。
7. **M33：真实浏览器验收与产品收口**。

## 7. 明确不做

- 不做只有聊天记录的通用 AI 壳；
- 不要求普通用户逐项填写八类硬件字段；
- 不把兼容规则编号和全量 Finding 放在首屏；
- 不让模型凭经验断言精确规格、价格或兼容性；
- 不做多 Agent 角色营销；
- 不先引入向量数据库、复杂工作流、爬虫或自动下单；
- 不删除现有规则引擎、检查历史、价格证据和报告能力。
