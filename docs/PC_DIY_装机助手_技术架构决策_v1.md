## 1. 结论先行

### 1.1 总体决策

**继续使用模块化单体，但把产品入口升级为“目标驱动的方案生成工作台”。** 现有确定性规则、目录、价格证据、检查历史和报告能力保留为可信内核；新增设计请求、方案草稿和受约束的 Agent 编排层。模型只能通过 typed tools 读取事实、生成候选和解释，不能直接写入正式 Build 或绕过规则校验。

推荐技术形态：

| 层 | 决策 |
|---|---|
| 应用形态 | 桌面优先 Web 应用，移动端可查看和轻量编辑 |
| 全栈框架 | Next.js + React + TypeScript |
| UI | 现有仪器白体系 + 共享 Zod 契约；结果优先，技术细节渐进披露 |
| 输入校验 | Zod；设计请求、方案草稿、Agent 事件和 API 共用明确 schema |
| 数据库 | V1 使用 SQLite；通过 Drizzle 迁移保持 PostgreSQL 路径 |
| 可信内核 | 自研纯 TypeScript 规则模块、目录事实和追加式价格证据 |
| Agent | 单助手、多技能、typed tools；不做多 Agent 角色营销 |
| RAG | 第一阶段使用结构化目录、别名、来源文档、价格快照和历史方案检索；不预装向量数据库 |
| LLM | 可插拔 OpenAI-compatible adapter；结构化输出、超时、降级，可关闭 |
| 价格数据 | V1 手工录入和用户提交证据；不做电商页面抓取 |
| 任务执行 | 先同步生成 + 追加事件；出现长任务后再局部引入队列/工作流 |
| 测试 | Vitest 单元/规则测试 + Playwright 端到端测试 |
| 部署 | Node.js Docker 镜像 + SQLite 持久卷；按触发条件迁移 PostgreSQL |

### 1.2 一句话解释

这是一个**关系型业务数据 + 确定性规则 + 受约束文本理解 + 方案编排**的产品。最需要自己控制的是：

- 用户目标和结构化意图；
- 标准型号目录与中国大陆型号归一化；
- 兼容性规则和自动校验；
- 带时间、来源和渠道的价格证据；
- 可回放的方案草稿、Agent 事件和用户决策；
- 用户接受后生成的正式项目、检查历史与报告。

LLM 是可替换的理解和建议能力，不是事实数据库，不是兼容性规则，也不是正式项目写入器。

## 2. 这次决策解决什么问题

本决策主要回答两个问题：

1. 是拉一个 GitHub PC 装机项目改造，还是从头做？
2. 如果从头做，选 Python/FastAPI、Java/Spring Boot 还是 TypeScript/Next.js？

结论不是“开源项目没有价值”。恰恰相反，开源项目可以帮助我们缩短数据和交互探索，但要把**可借鉴、可导入、可直接依赖、不可使用**分清楚。

## 3. 为什么不直接改造现成的 GitHub 项目

### 3.1 最像的项目：`a782987770/diy-pc-builder`

仓库：<https://github.com/a782987770/diy-pc-builder>

它对我们有参考价值，功能上包含：

- 八类配件；
- DIY 选配；
- 基础兼容性检查；
- 静态配件数据；
- Next.js + React + TypeScript；
- 简单 API 路由和 JSON 文件存储。

但它不适合作为产品底座：

- GitHub API 在仓库根目录没有找到正式 `LICENSE` 文件；README 中写的 “MIT” 不能替代清晰的授权文件；
- `package.json` 标记为 `private: true`；
- 数据是 72 条手工样例，包含静态价格和示例 CPS 链接，不是我们的价格证据模型；
- JSON 文件数据库无法支持项目版本、价格快照追加、证据审计和多用户数据隔离；
- README 将“价格自动更新脚本”列为后续计划，但没有可作为生产依赖的合规价格源；
- 它的产品定位偏向 CPS 导购和装机广场，而我们 V1 的核心是 DIY 清单检查、证据和可解释报告。

**结论：可以参考页面流程、字段命名和兼容性提示的交互方式；不复制代码，不复制数据，不把它作为 fork 起点。**

### 3.2 BuildCores OpenDB

仓库：<https://github.com/buildcores/buildcores-open-db>

这是目前最有价值的开源数据资源：

- 数据按 CPU、GPU、RAM、主板、机箱、电源、存储和散热器等类别组织；
- 有对应 JSON Schema；
- 字段覆盖插槽、内存类型、板型、显卡尺寸、供电接口、散热器高度等兼容性事实；
- 使用 ODC-By v1.0，允许分享、修改、创作和商业使用，但必须按要求署名并保留许可证声明；
- README 明确说明不提供价格和零售商特定数据；
- 数据以欧美产品和渠道为主，BIOS/CPU 支持列表仍是缺口；
- 上游数据持续更新，直接把远程仓库当运行时依赖会导致结果不可复现。

**结论：把它作为可审计的目录种子和 schema 参考，不把它当成中国市场最终目录，也不把它当成运行时远程 API。**

实际使用方式：

1. 记录上游仓库 URL、提交哈希、导入日期和许可证；
2. 离线导入经过筛选的产品记录；
3. 进入我们自己的 `canonical_products` 表后由本项目维护；
4. 对外发布时保留 ODC-By 署名和许可证说明；
5. 对缺少中国地区 SKU、BIOS 证据或关键尺寸的记录保留 `unknown`，不能补猜。

### 3.3 `docyx/pc-part-dataset`

仓库：<https://github.com/docyx/pc-part-dataset>

- 代码仓库使用 MIT；
- 数据来自抓取 PCPartPicker；
- 包含 USD 静态价格，但更新时间为 2025-07；
- 字段不足以支撑本项目的完整兼容性规则；
- 数据权利不能仅因为仓库代码是 MIT 就自动成立。

**结论：只能用作测试样本、字段对照或匹配评测参考，不进入生产目录和价格库。**

### 3.4 PCPartPicker 相关抓取/API 项目

代表项目包括：

- <https://github.com/JonathanVusich/pcpartpicker>
- <https://github.com/JonathanVusich/pcpartpicker-api>
- <https://github.com/lucwl/pypartpicker>

共同问题：

- 依赖非官方页面结构或抓取；
- 目标市场和中国大陆 SKU 不匹配；
- 有 GPL、无许可证或维护停滞等问题；
- 页面结构、访问限制和服务条款变化会直接使系统失效；
- 无法满足本项目“所有价格证据带来源、时间、渠道、商品状态且可审计”的要求。

**结论：只看解析思路，不作为生产依赖，不把抓取器隐藏在 V1 的链接处理功能里。**

### 3.5 Dify、LangGraph、n8n、Odoo 等平台

这些项目各自有价值，但与当前核心问题不匹配：

- Dify、LangGraph、n8n 重点解决模型调用和流程编排，而不是硬件目录、关系数据和确定性兼容性；
- Odoo、Saleor 等重点解决 ERP 或交易，不符合我们暂不做电商交易的范围；
- 直接依赖平台会让核心数据模型、审计和规则测试受制于平台抽象；
- V1 没有多 Agent、多步骤异步任务或复杂工作流需求。

**结论：V1 不以这些平台作为应用底座。未来确实出现复杂模型流程时，可以在边界模块局部引入，而不是从平台反向设计产品。**

### 3.6 ZCode 等开源 Agent 工作台（2026-09-23 补充）

仓库：`zai-org/ZCode`（Apache-2.0；社区分支 `Zcode-CE`）。曾评估"整体套用并改造其 UI"：

- **产品对象不匹配**：它是 AI 编程工作台（Electron 桌面 + Web + TUI + Agent CLI），UI 与交互全部长在编程场景上——文件树、diff、终端、测试结果、工具审批、checkpoint。装机决策台的核心画面（目标 → 方案 → 校验 → DIY）没有对应物，套用等于把方案审阅压扁成聊天流，正是 V2 明确不做的"通用 AI 壳"。
- **集成重量失控**：pnpm monorepo + Node ≥24 + Electron + RPC/provider 层 + SSH/WSL 远程 + SEA 打包。整体引入等于从"维护一个 Next.js 单体"变成"维护别人的基础设施子集"，与 §3.5 拒绝平台底座是同一条理由，且规模更大。
- **UI 优势不成立**：其深色 IDE/终端视觉正是用户 2026-09-20 已否决的"黑色大众 AI 面板"路线；整体换皮后 UI 价值归零、架构债务全留下。仪器白体系是三轮用户定向的差异化资产，不可放弃。
- **决策**：不整体套用。允许按许可证**逐件拆用**：
  - `ai-elements` 对话组件（Vercel 出品，Apache-2.0，npm 独立包，代码进自己仓库的模式）——M30+ 副驾抽屉可挑选 conversation / message / confirmation / tool 等组件 reskin 为仪器白，不必经过 ZCode；
  - 其 LLM 层使用 Vercel AI SDK（OpenAI-compatible provider）——印证 M30 计划：`infra/llm` 以 SDK 为库，而非自研 fetch，更不引入其框架；
  - 工具审批卡 / 事件流 / checkpoint 等交互概念已由 M28 的领域对象（确认卡、AgentEvent、方案版本）实现，方向自证，无需移植。

## 4. 从零自建与开源改造的比较

| 方案 | 初始速度 | 核心业务匹配 | 许可证/数据风险 | 后续维护 | 结论 |
|---|---:|---:|---:|---:|---|
| Fork 现成 DIY 项目 | 看起来快 | 低到中 | 中到高 | 高 | 不选 |
| Fork PCPartPicker 抓取项目 | Demo 可能快 | 低 | 高 | 极高 | 不选 |
| 基于 Dify/工作流平台 | 模型 Demo 快 | 低 | 中 | 中到高 | 不选作底座 |
| 基于电商/ERP 平台 | 交易能力强 | 低 | 中 | 高 | 不选 |
| **模块化单体从零实现** | **中** | **高** | **可控** | **中低** | **选择** |

“从零自建”不等于所有东西都手写：

- UI 使用成熟组件库；
- 数据校验使用 Zod；
- ORM 使用 Drizzle；
- 测试使用 Vitest/Playwright；
- 目录可以导入 BuildCores 的许可数据；
- LLM 使用官方 SDK 或 OpenAI 兼容客户端；
- 未来价格源使用适配器。

我们自己写的是无法从别的项目合法、可靠地搬过来的业务核心。

## 5. 为什么 V1 选 TypeScript/Next.js

### 5.1 选型考虑

| 维度 | TypeScript/Next.js | Python/FastAPI + React | Java/Spring Boot |
|---|---|---|---|
| V1 Web 交付速度 | 高：一个项目、一个语言、同源部署 | 中：前后端两套工程 | 中低：样板和分层更多 |
| 领域规则 | 很适合，纯函数和类型约束清晰 | 很适合，需额外类型纪律 | 很适合，但会偏重 |
| 前后端类型复用 | 原生共享 TypeScript/Zod | 需从 OpenAPI 生成或维护两套模型 | 需生成或维护两套模型 |
| LLM 结构化抽取 | 足够，SDK 和 Zod 可用 | 很强，Pydantic 生态成熟 | 可用，但迭代胶水较多 |
| 中文 OCR | V1 不需要；后续可接服务 | 最强，PaddleOCR 更方便 | 通常需要额外服务 |
| 单人维护 | **最优** | 中 | 较差 |
| 未来拆分 Python AI Worker | 可通过 HTTP/队列隔离 | 不需要拆分 | 通常仍需另加服务 |

本项目当前不是 OCR 产品，也不是大规模模型工作流产品。V1 最重要的是：

- 用户能够快速创建和编辑装机清单；
- 前后端的字段和状态不会漂移；
- 规则结果可以立即展示；
- 报告和价格证据交互清晰；
- 我们能快速根据真实用户反馈改变字段和流程。

在这个阶段，Next.js + TypeScript 能减少工程边界和重复类型定义。Python 并不是不适合，而是把 V1 不需要的 OCR/AI 运行环境提前引入了。

### 5.2 什么时候改为 Python 服务

只有出现以下事实之一，才新增 Python worker 或服务：

- 报价单图片/PDF OCR 进入正式范围；
- 需要 PaddleOCR、复杂文档解析或本地模型推理；
- 型号匹配实验需要大量 Python 数据科学工具；
- 某个明确的 AI 任务已经证明 Node 实现无法满足质量或成本要求。

即使届时引入 Python，也只隔离 OCR/模型任务，不重写已经稳定的项目、规则和价格证据核心。

### 5.3 为什么不选 Java/Spring Boot

Java 不是错误选择，尤其适合大型企业集成和长期后端团队。但当前是个人/AI 协作开发的绿色项目：

- V1 没有复杂事务、并发和企业系统集成要求；
- Spring Boot 的工程仪式和多层样板会增加首版反馈周期；
- Java 不能直接解决最难的目录质量、中文型号匹配和价格证据问题；
- 如果未来接入企业采购或商家后台，可以再把稳定领域 API 拆成 Java 服务，但现在没有必要为可能的未来预付成本。

### 5.4 为什么不用完整 LangChain/LangGraph

V1 中模型只做：

- 商品标题字段抽取；
- 用户意图和偏好结构化；
- 候选差异解释；
- 报告语言生成。

这些任务用一个明确的 `llm` 适配器、JSON Schema/Zod 校验、超时和降级就能完成。引入 LangChain/LangGraph 会增加抽象和版本约束，但不会提高兼容性规则的正确率。

未来若出现真正的长任务、人工中断、并行检索或检查点需求，再局部引入工作流框架。多 Agent 不是架构目标。

## 6.2 新增产品编排层

产品新增三个业务层对象，但不破坏既有 `Build` 数据：

```text
DesignRequest（用户目标）
    ↓
DesignProposal（Agent 候选草稿，可替换/修订）
    ↓ 用户接受
Build（正式方案，复用现有项目/清单/检查/报告）
```

配套追加式运行记录：

```text
AgentRun
  └─ AgentEvent[]（理解、检索、生成、校验、追问、接受、失败）
```

建议目录结构：

```text
src/
├─ agent/
│  ├─ runtime.ts          # 单助手运行编排和事件发射
│  ├─ tools/              # typed tools，只能通过应用服务访问事实
│  ├─ skills/             # 意图理解、方案生成、修订、解释
│  └─ guardrails.ts       # 候选/确认/正式 Build 边界
├─ application/
│  ├─ builds/
│  └─ design/             # request → proposal → validate → accept
├─ contracts/             # Zod 请求/响应和事件契约
├─ domain/
│  ├─ design/             # 意图、方案草稿、状态转换
│  ├─ build/              # 正式方案和八类配件
│  ├─ catalog/
│  ├─ rules/
│  └─ pricing/
└─ infra/
   ├─ llm/                # 可插拔模型适配器，可关闭
   ├─ retrieval/          # 目录/证据/历史方案检索适配器
   └─ db/
```

模型边界：

1. 模型输出必须经过 Zod 结构化校验；
2. 模型只能创建或修订 `DesignProposal`，不能直接写入 `Build`；
3. 精确规格、价格和兼容性需要工具返回的事实或规则结果支持；
4. 没有可靠数据时输出 `model_experience` 或 `unknown`；
5. LLM 失败时，保留目录候选、规则检查和高级 DIY，不能让整个产品不可用。

### 6.3 目标生成垂直切片

第一条可验收链路不等待真实模型：

```text
自然语言目标
  → 规则式/fixture 意图解析
  → 目录候选检索
  → 方案草稿
  → runBuildChecks
  → 方案审阅
  → acceptProposal → createBuild
```

用“2 万预算、白色海景房、剪辑和游戏”作为真实样本。先验证数据模型、信息披露和用户动作，再接入 OpenAI-compatible adapter，避免先做聊天接口却没有可用方案。

## 6.4 RAG 边界

第一阶段的检索上下文只来自可审计资料：

- 结构化硬件目录与别名；
- 规格来源和许可证；
- 用户提供的目标、清单和证据；
- 追加式价格快照；
- 已确认的历史方案和用户决策。

不把模型自己的常识当作精确事实。经验可用于组合倾向、取舍说明和缺失字段追问，但一旦落到尺寸、接口、预算数字或兼容性，必须回到结构化来源或明确标记未知。

## 7. 推荐项目结构

正式创建项目时建议采用以下结构，名称可以微调但职责不要混合：

```text
pc-diy/
├─ app/                         # Next.js 页面和 Route Handlers
│  ├─ (product)/                # 面向用户的页面
│  ├─ api/                      # 薄 API 层，只做鉴权/解析/调用服务
│  └─ layout.tsx
```

## 8. 关键数据边界

### 8.1 标准型号目录

我们自己的目录是产品事实层，至少分为：

- `canonical_products`：标准型号和归一化名称；
- `product_specs`：类别化规格；
- `product_aliases`：中文标题、厂商别名、常见缩写；
- `catalog_sources`：规格来源、来源 URL、采集时间、许可证和版本；
- `catalog_import_runs`：一次导入的上游提交、导入结果和错误。

> 2026-09-23 落地注记（M29）：以单表 `canonical_products` 起步（id / 类别 / 名称 / 别名 JSON /
> 决策规格 JSON / 来源 / ref_url），`product_aliases`、`product_specs`、`catalog_sources`
> 的拆表推迟到检索升级为 SQL/FTS 时再做——当前检索是进程内 substring 匹配，拆表没有消费方，
> 别名与规格的校验仍由类别 Zod schema 在读写两端承担。审计复用 `catalog_import_runs`。
> 数据来源边界（ZOL 参数离线补缺允许、电商平台抓取禁止、价格不进规格库）见业务规格 V2 §11.3。

BuildCores 记录进入这个层之前必须经过：

1. schema 校验；
2. 类别和字段映射；
3. 中国大陆 SKU 适配检查；
4. 缺字段标记；
5. 来源和许可证记录；
6. 导入版本固定。

### 8.2 价格证据

`price_evidence` 必须是追加式记录：

- 不覆盖旧价格；
- 不把“当前价格”作为唯一可变字段；
- 每条证据带来源类型、平台、店铺、商品状态、时间、价格口径和证据链接/附件；
- `manual_entry` 和 `user_submission` 是 V1 唯一启用来源；
- 未来联盟接口只能实现 `PriceSourceAdapter`，结果仍转换为同一个快照模型；
- 没有可靠证据就返回 `unknown`，不能让 LLM 填价格。

### 8.3 检查运行和旧结果

每次检查保存：

- 项目内容版本或规范化指纹；
- 执行时间；
- 使用的目录版本；
- 使用的价格证据 ID；
- 每条规则的 Finding；
- 报告生成版本。

项目配件或关键证据变化后，受影响的旧检查应标记为过期，而不是原地改写。

## 9. 价格数据路线

### 9.1 V1-A

- 用户手动填写型号和价格；
- 可以附商品链接、截图说明或备注；
- 系统保存为 `manual_entry`/`user_submission` 证据；
- 不自动抓取电商页面；
- 报告明确显示“价格由用户提供”或相应证据等级。

### 9.2 V1-B

- 允许粘贴商品链接；
- 只登记 URL、域名、用户提供的商品标题、价格和时间；
- 链接不能自动证明型号已经确认；
- 链接打不开也不能让整个项目失败，降级为手动补充。

### 9.3 V1-C 以后

如果真实用户验证了价格功能，再考虑官方联盟/开放平台：

- 优先评估京东联盟官方 API；
- 其次评估多多进宝或淘宝联盟，取决于资质和协议；
- 不依赖陈旧的第三方 SDK，优先直接对接官方文档；
- 所有返回值先转换成价格快照；
- 标注“推广视角、券后口径、佣金或跳转关系”；
- API 失效时熔断并保留历史证据，不影响兼容性检查。

明确禁止：

- 绕过反爬和验证码；
- 依赖非公开接口、破解接口或云市场转售爬虫 API；
- 把 GitHub 上无许可证的价格 CSV 放进生产数据库；
- 把联盟返回的优惠价伪装成中立市场最低价。

## 10. V1 不引入的基础设施

以下组件在 V1 不安装、不部署：

- Redis；
- Kafka/RabbitMQ；
- Celery/Temporal；
- 向量数据库；
- GraphRAG；
- 多 Agent 框架；
- 微服务网关；
- 独立搜索集群；
- Kubernetes；
- 大规模爬虫集群。

原因是 V1 的数据规模和任务耗时不需要它们。每增加一个基础设施，就增加一套备份、监控、升级和故障恢复责任。等真实指标证明需要时再加。

### 10.1 迁移 PostgreSQL 的触发条件

任一条件满足时再迁移：

1. 出现多个进程或多个实例同时写入；
2. 需要用户账户、共享项目和较高并发；
3. 需要复杂 JSON 查询或 PostgreSQL 特有索引；
4. 需要 pgvector 或全文检索；
5. SQLite 出现可测量的锁等待或备份问题。

在此之前，使用 UTC 时间、Drizzle migration、参数化查询和不依赖 SQLite 特有函数的 SQL，保持迁移可控。

## 11. 测试与质量门禁

### 11.1 规则测试

每条兼容性规则至少覆盖：

- 字段完整且通过；
- 字段完整且冲突；
- 关键字段缺失；
- 边界相等值；
- 两条来源互相冲突。

规则输出必须保证：

- `unknown` 不会自动汇总为 `pass`；
- 缺失字段永远显示；
- 每条结果包含规则编号和建议动作；
- 规则模块不访问网络和数据库。

### 11.2 型号匹配测试

建立带人工答案的 golden set：

- 中文商品标题；
- 品牌、系列和变体；
- 同系列多个长度/显存/散热版本；
- 散片、盒装、二手、海外版等差异；
- 缺字段和明显脏输入。

匹配测试输出准确率、候选率、误匹配率和未知率，不把模型返回的“confidence”直接当成质量指标。

### 11.3 端到端主链

Playwright 至少覆盖：

```text
创建项目
 -> 添加配件
 -> 查看/确认候选型号
 -> 发起检查
 -> 查看阻断/警告/未知
 -> 添加价格证据
 -> 查看预算和证据
 -> 修改配件
 -> 验证旧结果变为过期
```

## 13. 主要风险与处理

| 风险 | 影响 | 处理 |
|---|---|---|
| 中国大陆 SKU 目录不足 | 匹配和规则无法落地 | 先人工维护高频型号；BuildCores 作为种子，不假装覆盖本地市场 |
| 价格数据稀疏 | 用户觉得比价没有价值 | V1 明确卖“证据和检查”，不承诺最低价；允许用户贡献快照 |
| 型号变体误匹配 | 可能导致错误购买 | 先规范化/候选/确认；低置信度禁止静默选择 |
| 上游开源数据变化 | 结果不可复现 | 固定导入提交哈希和版本，运行时不依赖远程仓库 |
| LLM 幻觉 | 生成错误结论 | LLM 只抽取/解释；规则和价格字段由代码校验；失败降级 unknown |
| 价格源协议变化 | 价格模块失效 | 适配器、快照、熔断；兼容性和项目编辑不依赖价格源 |
| 过早复杂化 | 开发周期和维护成本上升 | V1 无 Redis、队列、向量库、多 Agent、微服务 |
| 外部项目许可证不清 | 商业合规风险 | 不复制无 LICENSE 代码；数据、代码和 API 分开审查 |

## 15. 进入编码前的检查点

架构已经可以定稿，仍需要在编码第一阶段并行完成两项业务验证：

1. 收集至少 20 份经过授权或脱敏的真实 DIY 装机/升级清单；
2. 访谈 5-10 名目标用户，确认他们愿意提供哪些输入、最在意哪类结果。

这两项不阻塞工程骨架，但会决定：

- 首批目录优先收录哪些型号；
- V1 先做全新装机还是升级；
- 价格证据在报告中的位置；
- 替代方案是否值得进入 V1-B；
- 是否需要登录、分享和历史保存。

### 最终决策

> **创建全新的 Next.js + TypeScript 模块化单体；自己实现业务模型、兼容性规则、价格证据和报告；通过可审计导入器吸收 BuildCores 的硬件规格数据；不 fork 现成项目，不使用爬虫价格源，不在 V1 引入多 Agent 或复杂基础设施。**

这套选择允许我们现在快速做出可用产品，也保留了以后接入官方价格 API、Python OCR worker、PostgreSQL 和更复杂 Agent 流程的边界，而不需要推倒重来。
