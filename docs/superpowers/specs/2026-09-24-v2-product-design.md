# RigMate V2 产品成型设计

> 状态：产品路线与首批体验基线。后续每个子项目另写可执行实现计划。
> 更新：2026-09-24。与 `docs/PC_DIY_装机助手_业务逻辑规格_v1.md` 共同约束产品；业务规则冲突时先修订业务规格。

## 1. 产品目标

让不熟悉硬件的新手用一句话得到一套合理、可修改、可追溯的 PC 配置。用户应能在同一处表达新需求、理解方案、检查依据、比较修订版本，最后保存或导出。经验用户可进入高级 DIY。

“合理”不是模型自称合理：候选必须有可识别的目录型号，决策规格要有来源，兼容结论来自确定性规则，价格标明证据日期或经验估算，资料不足明确显示。未验证的方案不得用“全部通过”或“放心购买”暗示确定性。

首批以**新装机新手**为主，覆盖现有 8 类核心配件；已有硬件、整机复核保留入口，升级方案的完整体验放在后续阶段。桌面优先，390px 手机宽度仍能完成核心任务。

## 2. 已有能力与差距

M33 已有目标输入、方案草稿、自然语言修订、相邻版本差异、接受进 DIY、检查历史和报告。LLM 当前只理解目标与修订意图；`src/domain/design/proposal.ts` 仍按预算档位挑固定候选，价格主要是代码内经验区间。目录有大量国际型号，但“条目数”不等于国内可买 SKU、字段完整度或来源可信度。方案页能显示来源等级和检查摘要，但缺少逐项可核验的“型号 → 规格字段 → 来源 → 规则结论”证据链。旧版方案已落库，前端尚不能切换查看。

这些差距决定开发顺序：先把用户体验和事实契约定型，再提高候选质量和生成能力，最后做部署与真实用户验证。前端原型可以先使用标记为**演示数据**的固定场景，但不能把演示结果接到正式接受/导出链路，也不能伪装成实时 Agent 运行。

## 3. 设计取舍

选择**前端体验先行、事实接口同步定型、后端逐步替换**。它让核心路径较早可评审，也保持每一步能与真实目录/规则对接。

不选“所有页面先出静态设计稿再开发”：难发现输入、追问、修订和窄屏状态问题。不选“先铺自由聊天，再补事实”：容易生成看似完整但无法验证的型号与结论。也不整体移植 Agent 框架：ZCode 的工作区密度、稳定输入、任务状态和侧栏层级可借鉴；RigMate 的主对象是装机方案而非代码任务。OpenClaw 类项目可参考会话组织，但具体第三方 UI 的成熟度、许可和适配性需逐项核验，不能作为代码依赖的默认依据。

参考： [ZCode 设计规范](https://github.com/zai-org/ZCode/blob/main/DESIGN.md)、[ZCode 仓库](https://github.com/zai-org/ZCode)、[OpenClaw 仓库](https://github.com/openclaw/openclaw)。

## 4. 页面与状态

### 4.1 入口 `/`

首屏是自然语言输入。用户可自由描述预算、用途、外观、已有硬件；预算单独输入为可选约束，显式预算覆盖文本识别。提供少量可点击并填入的真实示例、最近方案、复核已有清单与高级 DIY 入口。输入为空、预算无效、网络失败均在输入附近反馈，不丢失用户文本。

### 4.2 方案工作台 `/design/[id]`

主视觉是方案本身：用途适配、预算状态、8 类清单、关键取舍与必须确认的事项。用户的目标可查看和编辑；自然语言修订输入始终可见，桌面放在方案区底部，手机放在方案内容后的固定可达位置。主动作随状态改变：待确认时先回答问题，有阻断时先处理冲突，可接受时保存方案。版本入口能查看任一历史版本及差异，查看旧版不会悄悄覆盖最新版。

Agent 过程压缩为可读的阶段状态（理解、查询、组合、检查）；详细事件与来源按需打开。异步生成才显示真实进度；如果当前实现一次请求同步完成，只显示明确的等待状态，不伪造已经完成的分步动画。模型不可用时说明使用本地规则，无法可靠理解则追问并保留原输入。

### 4.3 硬件查询 `/hardware`

新手先看到 8 类硬件各自的作用、与哪些部件相关，以及当前目录能提供什么决策字段。搜索型号后显示精确型号、别名、已核规格、缺失字段、来源与更新时间；候选相似时让用户确认型号。未收录型号允许提交线索，但不自动当作已核事实。类别介绍是产品内容，不是开发说明。

### 4.4 正式项目与报告

`/projects` 展示方案进度、版本、最后检查状态；`/diy` 保留逐项编辑和规则详情；报告清楚区分已核事实、用户提供、经验估算与未知。证据台账仍是独立工作区，方案页通过上下文链接进入对应证据，不强迫新手先理解台账。

### 4.5 必备状态矩阵

| 状态 | 用户应看到 | 可执行动作 |
|---|---|---|
| 空白/首次进入 | 一个明显的输入入口和少量示例 | 输入目标、复核清单、DIY |
| 生成中 | 当前真实阶段与等待反馈 | 继续等待；失败可重试且文本保留 |
| 需要补充目标 | 一个会改变方案方向的问题 | 回答或修改原目标 |
| 方案就绪 | 配置、预算来源、取舍、检查摘要 | 修改、接受、查依据 |
| 待确认 | 具体缺口及其影响 | 回答、换件或进入 DIY |
| 兼容阻断 | 涉及的部件与可执行修复 | 修改方案；显式承担冲突后进 DIY |
| 修订完成 | 新旧版本变化和重新检查结果 | 继续修改、查看旧版、接受 |
| 模型/网络失败 | 哪一步失败、现有方案是否保留 | 重试、规则式继续、DIY |
| 目录无匹配 | 未找到已核型号，避免假匹配 | 换词搜索、手动输入、提交线索 |

## 5. 视觉与文案规范

延续 RigMate 的墨黑、仪器橙与浅色事实层，但重新组织层级：大面积空间给方案和自然语言输入；导航、状态、证据作为低噪声辅助。字体以清晰的中文正文为主，数字、价格、版本和型号用等宽或 tabular 数字。颜色只表达真实状态或主动作，避免装饰性渐变、卡片套卡片、工具日志墙、夸张的 Agent 拟人形象。桌面主区优先，侧栏可收起；手机单列并保持输入和主动作可达。

**产品文案与内部说明隔离**：页面只写用户要知道的事实、下一步和可操作按钮。“这里是什么模块”“模型不参与事实判断”等开发者说明放在设计文档；必要的事实边界用用户能理解的话在依据里表达，例如“兼容性由已核规格和规则检查，价格为经验估算”。演示数据明确标记，正式结果不能出现虚构的型号价格或来源。

每个状态至少做桌面 1280 与窄屏 390 截图验收，检查换行、遮挡、焦点、键盘操作、长型号与较长中文文本。视觉验收必须使用真实浏览器和真实产品文案。

## 6. 事实链与 Agent 契约

1. 意图理解：LLM 输出结构化需求，Zod 验证；显式用户输入优先。未配置/失败则本地解析或追问。
2. 候选检索：仅返回目录中可识别的型号与决定性规格；记录 `catalogId`、来源、数据日期和缺失字段。国际目录条目只有满足首批可用性门槛才进入默认推荐池。
3. 配置提议：模型在检索返回的有限候选中选择并给理由，服务端检查每个 `catalogId`、约束与价格出处。不得让模型生成任意精确规格或价格。模型失败时保留明确标注的规则式候选。
4. 自动检查：现有规则引擎验证组合；阻断、警告、未知分开呈现。用户已有配件若缺型号与规格，相关规则只能输出未知。
5. 证据呈现：每件部件可追到来源记录；每条重要结论可追到参与字段、规则和检查时间；预算区分价格快照、用户输入、经验估算与未知。
6. 版本与接受：修订产生不可变新版本；旧版可查看。正式 Build 只由用户接受后创建，接受前重新检查当前版本，避免过期结论被当作最新结果。

推荐的稳定前端视图契约为 `DesignWorkspaceView`：`goal`、`mode`、`runState`、`proposal`、`compatibility`、`decisionItems`、`provenance`、`versions`、`availableActions`。原型可用此结构的固定 fixture，正式接口再映射到同一契约；展示组件不自行猜来源、价格或检查结果。这个视图契约需在首个实现计划中用 Zod/TypeScript 明确定义。

## 7. 分阶段路线图

每阶段交付可运行软件，独立验收后再进入下一阶段；编号延续 M33，时间按实际验证结果调整。

| 阶段 | 目标与交付 | 退出条件 |
|---|---|---|
| M34 体验基线 | 实地走通当前核心路径，梳理信息架构、页面状态、视觉 token、用户文案；做可运行的入口/方案/修订/硬件查询原型，演示数据与真实状态明确区分 | 新手无需指导可找到输入、读懂方案、表达修改并查到 8 类硬件；桌面和手机关键状态截图评审通过；现有真实流程不回退 |
| M35 工作台接线 | 用统一视图契约替换原型数据；版本浏览、修改输入、追问、错误恢复、目录查询首屏和方案证据入口落地 | 所有核心操作连到真实 API；旧版只读、最新版可继续修订；失败不丢输入；E2E 覆盖完整路径 |
| M36 数据可信度 | 目录做国内高频型号白名单、别名确认、决策字段完整度与来源审计；样本清单和访谈驱动补录；价格证据接方案 | 首批推荐池的每个型号能查来源与关键字段；无依据字段不会显示为已核；样本覆盖有记录，无法覆盖的场景明确降级 |
| M37 受约束生成 | LLM 基于检索候选提出组合与理由，服务端验证并自动运行规则；保留规则式回退与版本历史 | 不存在模型凭空写入的型号/规格/价格；新手目标样本评测通过人工复核；冲突与 unknown 不被包装成通过 |
| M38 产品闭环 | 项目管理、报告、DIY、证据页在新视觉系统下统一；部署实测、备份恢复、错误观测、性能与安全基线；公开多用户前完成身份验证与项目隔离 | 可在目标部署环境稳定运行；数据可备份恢复；完整用户旅程在真实浏览器和部署环境通过；一个用户无法读取或修改另一个用户的项目 |
| M39 公开试用 | 5–10 名目标用户完成无指导任务；根据失败点修正文案、目录、追问和生成策略 | 完成率、错误类型、用户信任点有记录；高严重度误导或数据丢失问题清零；形成发布判断 |

M34–M35 是**前端优先**阶段，原型要可操作，但模拟数据绝不冒充正式结果。M36 与 M37 是让“好看的方案”真正可信的必要条件，不可跳过直接宣称产品完成。部署实测可在有 Docker 或目标服务器时穿插进行，不等待到最后才第一次运行。

## 8. 最终产品成型标准

一个首次使用的新手能在 5 分钟内描述目标、拿到至少一套有来源标识的配置、看懂预算与主要取舍、发现需要确认的事项、用一句话修改并比较版本、保存结果。对目录缺项、价格未知、兼容无法判定和模型故障，系统都给出诚实且可继续的路径。硬件查询能解释 8 类部件并核查推荐型号；正式项目可再次编辑、检查、导出，跨重启不丢失。

产品质量门槛包括：关键规则单测、方案/修订/接受 E2E、桌面和手机视觉验收、来源审计、固定样本集人工复核、部署后冒烟测试、备份恢复演练。公开多用户试用前验证身份、项目隔离与访问日志；若这些尚未完成，只能在受控的单用户环境试用。公开试用前不把覆盖率或测试数量当作可信度的替代品。

## 9. 下一步的实施边界

先为 M34 单独写实现计划，围绕入口、方案工作台、修订输入、硬件查询与关键状态，不在这一轮重写目录或规则引擎。M35–M39 在前一阶段反馈后分别形成小规格和实现计划；本文件维护终点、顺序与验收门槛，避免把长期路线伪装成不会变化的逐行任务表。每个里程碑更新 `docs/AI_COLLABORATION.md`，记录实现、证据、已知限制和下一步。
