# RigMate 上线级产品与 Agent 设计

日期：2026-10-14  
状态：深审设计稿，待评审  
范围：从当前代码状态到可供真实用户稳定使用的首个公开版本

## 0. 设计结论

RigMate 目前不需要重写内核，也不应该继续并行增加页面和 Agent 角色。上线前要完成一次“主流程收敛”：

1. 用户只需要围绕一个目标会话完成输入、追问、方案、修改和接受；
2. 数据库与规则是产品事实层，大模型是理解、取舍、解释和经验建议层；
3. 数据库外的型号可以由模型提出，但只能进入“待验证建议”，不能直接进入正式配置；
4. 召回先用结构化过滤、别名和可解释排序，暂不引入向量库；
5. 公开上线以事实支持率、召回质量、失败回退、延迟和数据覆盖为门槛，不以页面数量或模型调用次数为完成标准。

## 1. 深审得到的当前状态

### 1.1 已有的可复用资产

- 首页、设计会话、完整工作台和高级 DIY 已形成目标驱动、方案审阅和精调雏形。
- LLM 客户端已有 JSON schema、超时、重试、思考开关、请求准入和失败回退。
- Agent 已有 received → understanding → retrieved → composed → validated → answered 状态链。
- 候选只允许来自质量门后的 verified/supported 产品，兼容性由确定性规则执行。
- SSE 事件流、快照恢复、会话时间线、目录质量、字段证据和价格审核流已经存在。
- 离线评测和 live 选择评测脚本已经能比较规则选择与模型选择。

### 1.2 当前阻塞项

**产品层**：入口、会话、完整工作台、DIY、硬件中心和证据台的主次还不够清楚；方案卡和工作台的信息存在重复；模型建议、未知项和正式事实需要更强的视觉区分。

**Agent 层**：设计服务承担输入解析、检索、模型调用、方案保存和事件翻译，已经是 700 行级别的编排中心；创建和修订上下文没有统一契约；每类最多 12 条候选时八类可能暴露 96 条，模型容易被无关数据淹没；经验建议和数据库外产品线索还没有独立输出通道。

**数据层**：交接快照记录质量门后约 3126 条 supported 产品，但主板只有 19 条，verified 价格证据为 0。当前原始导入文件约为 hw-agent 723 条、BuildCores 26158 条、人工目录 49 条，原始数量不能代表可用覆盖。

**运维层**：实际支持的 LLM 环境变量比 .env.example 展示的更多；评测还没有统一的成本、延迟和发布阈值；数据备份、迁移、目录发布和静默 E2E 纪律需要转成正式发布清单。

## 2. 首个公开版本的产品定义

### 2.1 用户承诺

用户说出预算、用途、偏好和已有硬件后，RigMate 能在可解释的时间内给出一套能继续修改的装机方向，并明确告诉用户：哪些是目录事实、哪些是规则结果、哪些未知、哪些只是模型经验建议。

### 2.2 不承诺的能力

- 不承诺实时最低价；
- 不承诺覆盖所有市场型号；
- 不承诺模型记忆中的规格适用于具体变体；
- 不把数据库外建议直接变成正式清单；
- 不用开放式聊天掩盖资料缺失。

### 2.3 核心指标

1. 首次目标到可审阅方案的成功率；
2. 用户能否理解来源并完成一次修改；
3. 正式配置的事实支持率和兼容性准确率；
4. 每次会话的延迟、模型成本和回退率。

## 3. 目标用户流程

~~~text
首页输入目标
  → Agent 解析预算/用途/偏好
  → 只追问一个最影响结果的缺口
  → 显示检索进度与候选摘要
  → 展示正式配置、预算状态、兼容摘要和依据
  → 用户自然语言修改
  → 生成新版本并显示差异
  → 接受进入 Build 或进入 DIY
~~~

追问优先级固定为：预算口径、主要用途、已有关键硬件、尺寸/电源限制、地区。一次默认问一个问题，只有两个字段强耦合时才合并。

高级用户可以从方案进入 DIY，逐项替换或补充自有硬件；DIY 继续使用正式 Build、规则引擎和检查历史，不强行经过 Agent。

## 4. 前端信息架构

### 4.1 三层导航

**开始**：首页目标输入、新建会话。  
**我的方案**：会话列表、方案历史、已接受 Build。  
**数据与核验**：硬件目录、证据台、审核队列，默认弱化为运营入口。

设计详情页默认是会话视图，完整工作台通过明确按钮进入，DIY 只在用户选择后进入。

### 4.2 会话页固定布局

1. 顶部：方案标题、运行状态、来源模式；
2. 中部：用户消息、理解摘要、检索块、方案卡和版本差异；
3. 右侧或内联：预算尺、兼容摘要、未知项和依据抽屉；
4. 底部：常驻修改输入框，明确当前是补充目标还是调整方案。

生成中只展示真实事件。事件块默认显示摘要，展开才显示候选 ID、证据数量和回退原因。

### 4.3 方案卡信息顺序

方案卡依次显示：方案定位、预算与价格证据、八类配置、兼容摘要、主要取舍、未知/待确认、模型建议、接受/调整/DIY。

正式配置、待确认事实和模型建议必须使用不同区域、标签和颜色。数据库外产品线索不进入配置表、不显示为价格行、不影响接受按钮。

移动端采用单列，依据用抽屉，底部输入框不能遮挡主要操作，状态不能只靠颜色表达。

## 5. Agent 目标架构

### 5.1 四条职责边界

**理解层**：LLM 将当前消息和会话摘要映射为结构化意图。显式预算、用户明确保留的部件和已确认字段由服务端覆盖模型输出。

**召回层**：服务端负责规范化、分类、硬约束、质量门、字段质量、价格证据和排序。LLM 不直接查询数据库。

**选择层**：LLM 只返回候选池内的 canonicalId、类别和理由码。守卫拒绝候选池外 ID、质量不达标、类别不符和越权字段。

**建议层**：LLM 可以返回 experience_advice 或 external_product_hint。这两类结果有独立来源标记，不能改变正式配置、价格合计或兼容结果。

### 5.2 统一会话上下文

服务端为每轮生成结构化摘要，不把完整事件历史塞给模型：

~~~ts
type ConversationContext = {
  requestId: string;
  turn: number;
  intent: StructuredIntent;
  confirmedFields: string[];
  pendingQuestion: string | null;
  latestProposal: { id: string; version: number; selectedIds: string[] } | null;
  latestTradeoffs: string[];
  latestFindings: Array<{ ruleId: string; status: string; conclusion: string }>;
  recentUserMessages: string[];
};
~~~

模型只收到最近两轮消息、结构化摘要和当前任务需要的候选事实，完整事件保留在数据库用于审计和页面恢复。

### 5.3 正式配置与模型建议契约

正式配置项必须满足：catalogId 存在且类别一致、质量状态可用、规格来自候选记录、价格为空或来自已审核证据、兼容性重新由规则运行。

模型建议项只能包含类别、标题、解释、建议类型、是否需要验证和可选的外部产品名称。不得包含未经证据支持的价格、尺寸、接口、功耗和兼容结论。

### 5.4 调用次数和上下文预算

交互轮次最多三次模型调用：意图解析、候选选择、非阻塞经验建议。

候选池默认每类 6 条；精确型号命中可扩到 20 条；多样性补召回最多 2 条。输入目标控制在 6k～10k tokens 内，输出只给结构化 JSON。

思考模型耗时过长时，候选选择先使用快速策略；经验建议绝不能阻塞正式方案。

## 6. 召回与重排

### 6.1 召回顺序

1. Unicode、大小写、空格、连字符、中文数字和单位规范化；
2. 型号、MPN、系列名、中文名和别名精确/前缀命中；
3. 类别和已有部件排除；
4. 插槽、板型、接口、长度、功耗等硬约束过滤；
5. 用途、外观、静音、升级空间匹配；
6. 质量、字段完整度、价格证据新鲜度和性能档位重排；
7. 去重并记录进入和落选原因。

### 6.2 候选解释

每个候选必须能解释为什么进入前 N：型号/别名命中、用途命中、必填字段完整度、已审核价格、未知字段、硬约束保留或排除。

模型看到的是白名单 decisionSpecs，不看到原始数据库对象、SQL、文件路径和原始网页。

### 6.3 空结果

没有候选时不返回相似型号冒充命中。系统要说明缺少哪个类别或字段，并提供一个最小动作：放宽预算、补尺寸、指定地区、等待审核或进入 DIY。

## 7. 数据上线计划

### 7.1 数据分层

原始导入层保存来源和版本；规范目录层保存 canonical product 和决策字段；质量层保存字段证据和发布状态；价格层保存追加式快照；展示层保存中文名和链接。任何一层都不能用经验值覆盖规格事实。

### 7.2 首版最低覆盖

- 八个类别每类至少 30 条 supported 候选；
- CPU、GPU、主板、电源每类至少 10 条 verified 候选；
- 至少 30～50 条 verified 价格证据，覆盖主要预算档；
- 热门 CPU/GPU/主板有中文名、英文名、别名和关键决策字段；
- 主板 socket、供电、M.2、内存类型和板型优先补齐；
- 显卡长度、供电接口和功耗优先补齐；
- 电源额定功率、接口和质量状态优先补齐。

### 7.3 数据缺口回收

每次空结果、unknown、用户手动输入未命中型号或模型重复建议外部型号，都记录匿名缺口事件。运营每周按频次补目录，不能通过放宽质量门提高表面召回率。

## 8. 分期交付

### Phase 0：冻结产品边界

产出页面地图、主流程、来源标签、错误状态和指标定义。停止新增独立入口、通用聊天、实时价格、向量库和多 Agent。

完成条件：新手从首页到方案接受不需要理解数据库、规则编号或八类规格字段。

### Phase 1：数据发布基线

产出核心类别覆盖报表、主板/价格补池、别名评测集、空结果样本、来源和备份清单。

完成条件：达到第 7 节最低覆盖目标，data-release-gate、typecheck、lint、test 和 build 全通过。

### Phase 2：Agent 上下文和召回

产出会话摘要、规范化召回、候选白名单、动态 K、候选落选原因和修订上下文。

完成条件：连续三轮预算/用途 → 外观/静音 → 已有部件不会丢字段；精确型号和别名召回有固定指标；无候选时不凑数。

### Phase 3：混合建议层

产出经验建议 schema、数据库外产品提示、来源标签、独立事件、失败回退和持久化。

完成条件：模型可以发挥，但建议不能修改正式配置、价格和兼容性；模型失败不影响方案生成。

### Phase 4：前端信任层

产出正式配置/未知/模型建议三分区、依据抽屉、真实事件状态、版本差异和移动端完整操作。

完成条件：新用户能看懂哪些能直接用、哪些要确认、哪些只是建议，并能完成一次修改和接受。

### Phase 5：评测和观测

产出离线样本、live 报告、run 审计、延迟/成本/失败指标、管理员诊断面板和 feature flag。

完成条件：模型、Prompt、召回器和建议层都可以独立比较、灰度和回滚。

### Phase 6：发布

顺序为内部 Alpha → 5～10 名 Beta 用户 → 小流量公开。每阶段把真实问题加入回归集后再扩大范围。

## 9. 代码实施边界

Agent 线：新增会话摘要、模型白名单上下文、建议调用和验证；拆分设计服务为 request、generation、revision、persistence 适配模块。

前端线：收敛首页、会话页和完整工作台；方案卡增加依据、未知和模型建议区域；历史方案和 DIY 保持可达但不抢主流程。

数据线：补齐目录审核、来源版本、缺口队列、价格证据和评测数据；所有导入先备份并跑数据门禁。

当前并行目录/中文展示工作线的文件继续避开；共享 schema、迁移和 catalog ranking 改动需要先对照 AI_COLLABORATION.md 登记并单独验证。

## 10. 发布门槛

### 10.1 事实与安全

- 正式方案精确规格、接口、尺寸、价格和兼容性 unsupported claim rate 为 0；
- 候选池外产品进入正式方案次数为 0；
- 规则冲突被显示为通过次数为 0；
- 密钥、内部提示词、文件路径和其他用户数据泄露次数为 0；
- 未授权写工具调用次数为 0。

### 10.2 质量与体验

- 结构化模型输出通过率至少 99%；
- 精确型号 Recall@20、空结果准确率和约束违规率达到冻结阈值；
- 无 LLM key 时目标输入、规则方案、兼容检查和 DIY 仍可用；
- 正式方案交互 P95 目标不超过 30 秒，建议调用不阻塞主结果；
- 桌面和 390px 移动端均能完成输入、查看依据、修改和接受。

### 10.3 运维

- 数据库迁移可重复，写库前自动备份；
- 目录发布有来源版本和抽样记录；
- 每个 AgentRun 有 prompt/model/retrieval/fallback/latency/cost 摘要；
- Prompt、模型、召回器和建议层都有可配置回退；
- E2E 在清理 3000 端口 dev server 的静默机器上通过；
- 发布包包含环境变量、数据恢复、日志脱敏和故障切换说明。

## 11. 风险排序

最高风险是数据覆盖不足，解决方法是补池和发布门，不是放宽模型约束。其次是思考模型等待过长，应减少候选上下文、分离建议调用并快速回退。第三是用户混淆经验与事实，应使用三分区、来源标签和依据抽屉。第四是编排中心过重，应拆分服务但保持 API 和事件契约。第五是并行开发覆盖文件，应按工作线登记并把共享契约单独验证。

## 12. 执行顺序

1. 评审并冻结产品主流程和来源标签；
2. 完成目录覆盖报表和主板/价格补池；
3. 接入会话摘要、动态召回和候选白名单；
4. 增加独立经验建议通道；
5. 重整方案卡、依据抽屉和移动端；
6. 建立评测、成本、审计和灰度发布；
7. 先内部 Alpha，再决定是否扩大公开范围。

在第 1 步完成前，不继续添加新的页面、模型角色或外部数据源。上线级产品的关键不是让模型更会说，而是让用户知道哪些内容可以信、哪些内容还需要确认，并且在模型失效时系统仍然可用。
