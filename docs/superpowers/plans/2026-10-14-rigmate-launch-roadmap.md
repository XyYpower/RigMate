# RigMate 从当前状态到可上线的产品路线图

日期：2026-10-14  
状态：规划中  
目标：把 RigMate 收敛成一条稳定、可信、可持续运营的装机决策主流程。

## 一、上线版本要解决的问题

上线版本不追求“什么都能聊”，只解决一个清晰问题：

> 用户说出预算、用途、外观和已有硬件后，RigMate 能生成一套可解释、可校验、可继续调整的装机方案。

正式方案中的产品、规格、价格和兼容性由目录、证据和规则确认。大模型负责理解、排序、解释和提出经验建议；数据库外的产品只能进入“待验证建议”，不能直接成为正式配置。

目标主流程固定为：

~~~text
输入目标 → 补一个关键问题 → 召回候选 → 生成方案 → 查看依据 → 调整 → 接受 / 进入 DIY
~~~

暂不把实时全网比价、自动下单、开放式聊天、向量数据库、多 Agent 和 OCR 采购单作为首个公开版本的前置条件。

## 二、当前基线和主要风险

当前仓库已经有 Next.js 16、SQLite、目录质量门、兼容规则、方案生成、LLM JSON 客户端、SSE 会话流和会话式 UI 原型，基础能力不需要推倒重写。

需要优先解决的风险：

1. **产品路径过多**：首页、方案会话、完整工作台、硬件中心、证据台和审核台之间的主次关系还不够明确。
2. **LLM 上下文太薄**：现有调用偏向一次性意图解析和候选选择，修订时模型看不到足够的会话摘要、上一版理由和兼容结果。
3. **召回结果不够结构化**：候选虽然经过质量门，但模型看到的规格、缺失字段、价格证据和取舍原因没有清晰分层。
4. **数据覆盖不均衡**：当前质量门后的总量不等于可用覆盖，主板和已审核价格仍是明显短板。
5. **缺少上线指标**：还没有稳定的多轮样本、召回样本、成本预算、P95 延迟和事实支持率门槛。

## 三、产品收敛方案

### 3.1 面向普通用户的三页主线

**首页**只做目标输入：预算、用途、外观、已有硬件可以一次描述，也可以分轮补充。页面只保留一个主要动作“开始生成方案”。

**会话页**是默认工作面：展示用户消息、Agent 理解、召回进度、方案卡、依据、未知项和调整输入。模型建议与正式配置分开显示。

**完整工作台**服务需要精调的用户：展示逐件规格、兼容核验、证据来源、版本差异和进入 DIY 的入口。

硬件中心、证据台、审核台、方案历史属于运营或高级用户入口，不抢占新手主流程。

### 3.2 结果卡片必须区分三类信息

- **正式配置**：有 canonicalId，经过质量门和兼容规则，可接受。
- **待确认事实**：字段缺失、价格无证据或规则返回 unknown，需要用户确认。
- **模型建议**：经验取舍或数据库外产品线索，标明“不会参与当前价格和兼容检查”。

### 3.3 首版明确不做

- 不做通用闲聊和自由 Markdown 长回答；
- 不把模型记忆中的规格、价格写入方案；
- 不让数据库外产品自动进入正式配置；
- 不以实时电商价格作为上线依赖；
- 不引入多 Agent 编排和向量库来掩盖结构化数据不足。

## 四、后端 Agent 目标架构

### 4.1 四个职责

1. **Intent parser**：把当前消息和会话摘要转成结构化意图，服务端覆盖用户明确输入。
2. **Retriever**：规范化型号、别名、中文俗称和用途词；执行类别与硬约束过滤；返回带质量、价格、证据和召回理由的候选。
3. **Selector**：只允许从候选 ID 中选择正式配置；选择理由使用枚举理由码和系统渲染文字。
4. **Advice planner**：允许模型根据自身知识提出经验建议或数据库外产品线索，但必须带来源标签和待验证标记。

### 4.2 一轮请求的调用预算

一轮最多三次 LLM 调用：意图解析、候选选择、可选建议。建议调用超时或失败不阻断正式方案。

候选上下文先在服务端压缩：每类 6 条主候选加 2 条不同性能档位候选，候选不足时诚实返回空结果。模型不接收 SQL、文件路径、原始网页或完整数据库行。

### 4.3 数据边界

数据库是以下内容的唯一事实来源：型号、规格、接口、尺寸、功耗、价格、证据、兼容性。

模型知识可以用于：用途理解、性能取舍、升级方向、经验解释、数据库外产品线索。

数据库外线索必须进入独立的 advice 字段或事件，不能被映射为 proposal item，不能参与价格合计，不能传给接受方案的写路径。

### 4.4 失败和回退

模型不可用、超时、schema 拒绝、候选 ID 非法时，使用同一候选集的规则排序。回答规划失败时渲染系统模板。所有回退都写入事件，用户看到真实状态，不把规则路径描述成模型智能选择。

## 五、数据建设路线

### P0：先补能影响决策的字段

优先级为 CPU、GPU、主板、电源，其次是散热器、机箱、内存、存储。每条产品先确保决策字段完整，再扩展展示字段。

必填字段缺失时留空并标记 unknown，不能用同系列产品推测。规格字段不翻译，中文名只存在展示层。

### P1：从“总条数”改成“有效覆盖”

公开试用前的最低目标：

- 每个类别至少 30 条 supported 候选；
- CPU、GPU、主板、电源至少各 10 条 verified 候选；
- 至少 30～50 条 verified 价格证据；
- 热门型号有别名、中文展示名、关键决策字段和来源；
- 每个类别都有精确型号、别名、错别字和无结果样本。

当前主板和 verified 价格不足时，产品可以继续内部使用，但不应把预算排序宣传成完整能力。

### P2：建立数据运营循环

每次用户看不到候选、修改方案或进入 DIY，都记录匿名化的缺口类别和字段。每周从缺口中选择一批产品进入审核链，补齐来源和字段，再重新跑数据门禁。

## 六、前端重整路线

### Phase 1：信息架构

- 首页只有目标输入和示例目标；
- 会话页默认展示进度与方案，不再让用户在多个工作台之间跳转；
- 方案卡上直接显示预算、正式配置、未知项和模型建议；
- 高级 DIY 从方案卡进入，不作为新手默认入口。

### Phase 2：视觉和交互统一

- 统一页面头部、状态徽章、按钮层级、间距和移动端断点；
- 生成中显示真实事件，不显示假的固定步骤动画；
- 失败状态提供“补充信息”“使用规则模式”“进入 DIY”三种明确动作；
- 依据面板默认折叠，点击后显示字段、来源、日期和规则号。

### Phase 3：信任表达

在每个结果旁明确显示：来源类型、质量状态、价格是否有证据、是否经过兼容检查。模型建议区域使用独立颜色和标签，避免用户把经验判断当成产品事实。

## 七、评测与上线门槛

### 7.1 必备评测集

建立脱敏的固定样本，覆盖：

- 正常预算与用途；
- 中文俗称、型号别名、错别字；
- 只有用途没有预算；
- 多轮补充和修改；
- 已有硬件和互相冲突的偏好；
- 数据库无结果；
- 候选规格缺失；
- 模型提示词注入和要求泄露内部信息。

### 7.2 上线前指标

- 精确型号 Recall@20 ≥ 90%；
- 硬约束违规率 = 0；
- 精确规格、价格、接口和兼容性 unsupported claim rate = 0；
- 候选池外产品进入正式方案的次数 = 0；
- 规则冲突被显示为通过的次数 = 0；
- 无 LLM 配置时主流程成功率保持可用；
- LLM 失败回退率、schema 失败率、P95 延迟和 token 成本都有记录。

交互版本建议把正式方案的 P95 控制在 30 秒内；超过预算或超时直接展示规则结果，经验建议异步补充。

## 八、发布顺序

### 内部 Alpha

只开放给开发和数据审核人员。目标是验证目录覆盖、规则结果、事件日志和回退，不追求模型文案漂亮。

### 小范围 Beta

开放给 5～10 名真实用户，记录：用户是否理解来源标签、是否接受方案、最常修改的部件、无法召回的类别和模型建议误导点。

### 公开版本

满足数据门禁、评测门槛、成本上限、错误恢复、数据库备份和隐私检查后再开放。模型建议功能可以先默认开启，但数据库外产品必须保持待验证状态。

## 九、建议的执行顺序

1. **产品收敛**：冻结首页、会话页、方案页三页主线，清理重复入口。
2. **数据补强**：先补主板、价格证据和热门型号别名，建立评测样本。
3. **Agent 重构**：加入会话摘要、分层召回和独立 advice lane。
4. **前端信任层**：显示依据、未知项、回退状态和模型建议标签。
5. **评测与观测**：接入召回、事实、延迟、token 和成本指标。
6. **内部 Alpha**：用真实样本验证整条链路。
7. **Beta 和发布**：根据真实反馈补数据、修召回、调 prompt，再扩大范围。

在这份路线图评审通过前，不继续增加新的页面、模型角色或外部数据源。先把主流程、数据事实边界和上线门槛固定下来。
