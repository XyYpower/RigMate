# RigMate 数据来源获取与发布设计

版本：1.0
日期：2026-09-29
目标：建立一条可追溯、可暂停、可替换、合规的数据获取流水线，而不是一次性编写不可维护的全网爬虫。

## 1. 总体决策

RigMate 不做“爬全网硬件数据”。不同事实由不同来源提供，所有来源先进入待处理层，再经过字段级审核，最后才进入 Agent 可用目录。

来源注册表 → 合规获取适配器 → 原始快照层 → 字段提取与身份匹配 → 证据记录与冲突检测 → 人工/规则审核 → canonical_products 发布层 → 检索、兼容规则和 Agent。

Agent 永远不直接读取原始网页，也不能把搜索结果直接写入 canonical_products。

## 2. 四层来源策略

### S1：厂商官方来源

用于八类硬件的规格事实。来源包括公开产品页、规格页、用户手册、安装手册、数据表、CPU 支持列表和 BIOS 兼容列表。

获取方式：优先使用公开静态 HTML、公开 PDF 和官方下载链接；保存 URL、页面标题、访问时间、内容哈希；解析器只提取 schema 允许的决策字段；页面结构变化时任务失败并进入人工队列，不静默发布空值。

### S2：开源结构化来源

BuildCores OpenDB 用于发现型号、别名和基础规格。它有 ODC-By 许可和 schema 校验，但不是厂商官方数据，也不提供价格。

获取方式：固定 upstream commit 离线导入；保存仓库、commit、许可证、导入时间和统计；只作为候选和补充，不覆盖已有 S1 字段；不把所有导入记录自动标记为 verified。

### S3：专业第三方资料

用于交叉核对和补充厂商没有明确给出的测量字段。第三方实测长度、功耗、温度和噪音必须保留测量口径，不能自动覆盖厂商规格。人工选择来源，保存文章、测试页面、日期、设备版本和引用段落。

### S4：用户和授权商业来源

用于购买价格、本地 SKU、实际库存和用户已有硬件。价格不能来自模型估计或未经授权的电商爬取。用户手动录入或上传凭证后进入审核队列；未来只接正式授权联盟 API 或供应商报价接口。

## 3. 各类数据推荐获取方式

| 数据 | 首选方式 | 次选方式 | 当前不采用 |
|---|---|---|---|
| CPU socket/TDP | AMD/Intel 官方页和规格 PDF | BuildCores 交叉核对 | 模型记忆、论坛 |
| 主板插槽/板型/内存支持 | 厂商规格页和用户手册 | BuildCores 补缺 | 电商标题 |
| GPU 长度/接口 | 具体显卡厂商型号页和安装手册 | S3 实测 | 芯片公版数据推断非公版 |
| 机箱显卡限长/散热器限高 | 机箱厂商规格页和布局手册 | S3 实测 | 宣传图推断 |
| 电源功率/接口 | 电源厂商规格书和线材表 | 可信拆解 | 认证等级推断接口 |
| 散热器高度/socket | 厂商安装手册和兼容列表 | 专业评测 | 水冷泵头尺寸推断风冷高度 |
| 型号别名 | 官方型号、MPN、人工整理 | BuildCores | 模型自动生成 |
| 价格 | 用户凭证、手动录入、授权 API | 审核报价 | 未授权电商爬虫 |

## 4. 适配器设计

每个来源使用独立 adapter，不让页面、Agent 或通用爬虫直接处理来源内容。

SourceAdapter 必须提供 sourceKey、sourceTier、allowedDomains、license、fetch、parse 和 identity 方法，并具备超时、限速、最大响应大小、内容类型检查、失败原因、内容哈希和版本信息。

第一批适配器：buildcores-git、manufacturer-manual、manufacturer-page、user-evidence。不要一开始为每个品牌写独立爬虫，先验证 20–30 个型号的字段提取流程，再决定哪些品牌值得自动化。

## 5. 原始快照层

每个快照保存 snapshotId、sourceKey、sourceUrl、fetchedAt、httpStatus、contentType、contentHash、upstreamVersion、rawPath、parserVersion、extractionStatus 和 failureReason。

原始快照只供审核和重新解析使用，不直接返回前端，不参与 Agent 检索。页面变化后生成新快照，不能覆盖旧快照。

## 6. 字段提取与身份匹配

1. 识别品牌、系列、完整型号、MPN 和地区。
2. 与已有 canonical product 做精确 MPN 匹配。
3. 没有 MPN 时要求品牌、完整型号和变体字段至少两个匹配。
4. 只提取 schema 允许的决策字段。
5. 保存字段原文摘录、单位和页面位置。
6. 无法确认身份时进入 pending_catalog_queue，不自动合并。

同一个芯片系列、不同板卡品牌、不同散热器、不同颜色 SKU、不同容量套装和不同地区型号默认视为不同变体。

## 7. 发布状态机

discovered → snapshot_saved → extracted → identity_matched → evidence_reviewed → published。

异常状态：needs_identity、needs_field_review、conflicting、stale、rejected。只有 published 的字段才允许进入推荐池。partial 产品可以被搜索，但涉及缺失字段的兼容规则必须返回 unknown。

## 8. 获取频率

规格和手册在首次录入、发现冲突和产品改版时复核；高搜索型号每季度检查来源是否可访问和内容哈希是否变化；新品队列在用户搜索未命中后进入人工审核；价格每条快照按日期过期；BuildCores 按固定 commit 手动导入并生成差异报告。

## 9. 合规和稳定性边界

只访问公开页面和允许使用的接口；不绕过登录、验证码、付费墙、反爬或访问控制；不抓取京东、淘宝等平台的登录态和未授权价格数据；遵守 robots、服务条款、许可证和署名要求；不把大规模原始网页提交到 Git；页面结构变化时失败并报警，不静默写入错误字段。

## 10. 第一条数据垂直切片

先做一条“白色 2 万预算、剪辑 + 3A 游戏”数据链，选择 20–30 个具体产品变体：CPU 3 个、主板 4 个、GPU 6 个具体品牌型号、电源 3 个、机箱 4 个、散热器 3 个、内存和固态各 3 个。

每条记录至少补齐影响兼容的字段、官方来源 URL、字段摘录、核验日期、中文别名和质量状态。价格先不接自动来源。

## 11. 验收标准

1. 每个推荐候选都能打开至少一个具体来源。
2. GPU 长度、机箱限长、散热器高度、电源接口和主板 socket 的证据覆盖率为 100%。
3. 每个候选都能区分具体品牌变体，不用芯片系列替代板卡型号。
4. 缺字段、冲突和过期数据不会显示为兼容通过。
5. 用户输入别名可以命中正确 canonicalId，错误别名不会跨类别命中。
6. 来源不可用时系统保留旧快照并标记需要复核。

## 12. 实现顺序

1. 增加 source registry 和 raw snapshot 数据结构。
2. 把现有 BuildCores 导入器接入统一审计格式。
3. 用人工官方 URL/PDF 完成 GPU + 机箱小样本。
4. 建立字段级审核和发布脚本。
5. 用真实目标跑检索、兼容和 UI 依据展示。
6. 评估人工耗时和字段冲突，再决定是否自动化某个品牌页面。
7. 通过后扩展到 CPU/主板、电源和散热器。

## 13. 不可逆决策延后

在小样本完成前，不决定向量数据库、不决定全站爬虫框架、不决定大规模异步队列、不决定多供应商价格聚合，也不把 BuildCores 的所有字段迁移成 verified。
