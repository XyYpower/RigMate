# PC DIY 装机助手：业务逻辑规格（V2）

> 文档状态：产品方向重校准后的业务单一事实来源
> 版本：2.0
> 更新日期：2026-09-23
> 适用范围：中国大陆市场假设下的 PC DIY 装机与升级决策

## 1. 产品定义

RigMate 是一个面向 PC 装机与升级决策的 Agent 工作台。用户可以用自然语言描述目标，系统自动理解预算、用途、外观和优先级，检索硬件资料，生成一套可编辑方案，并自动校验关键风险。

示例：

> 我想配置一台 2 万预算的白色海景房主机，主要为了做剪辑和打游戏。

系统的第一价值不是让用户填写完整硬件表，而是把模糊目标变成：

1. 一套清晰、可修改的候选方案；
2. 一组有依据的预算和取舍；
3. 自动发现的冲突、未知和需要确认的事项；
4. 用户可以接受、继续对话修改或进入高级 DIY 的正式项目；
5. 一份可以保存、复核和导出的结果。

RigMate 不是电商平台，不自动下单，也不是只会聊天的通用 AI 壳。

## 2. 用户与入口

### 2.1 默认用户

- 有预算和用途，但不想先理解全部硬件字段的新手；
- 有明确偏好，希望 Agent 先给一套方案再调整的用户；
- 熟悉硬件、希望直接替换组件并保留自动校验的 DIY 玩家；
- 已有一份配置单，希望快速复核和改造的用户；
- 需要升级现有设备的用户。

### 2.2 三种入口

1. **从目标开始**：自然语言描述预算、用途、外观、性能优先级和已有硬件。
2. **从清单开始**：粘贴配置单、商品标题或链接，由系统识别成方案草稿。
3. **自由 DIY**：进入高级编辑，逐项选择和替换硬件；每次修改自动校验。

三种入口最终都进入同一份方案状态，不创建互相孤立的产品。

## 3. 核心业务对象

### 3.1 设计请求 DesignRequest

保存用户原始目标和结构化意图：

- `rawInput`：用户原始文本；
- `budgetCents`：预算，可为空；
- `useCases`：游戏、剪辑、开发等用途；
- `appearance`：白色、海景房、静音、RGB 等偏好；
- `performanceTargets`：分辨率、软件、帧率或生产力优先级；
- `existingParts`：用户已有硬件；
- `region`：地区；
- `constraints`：排除项、必须保留项和取舍顺序。

### 3.2 方案草稿 DesignProposal

Agent 针对一次设计请求生成的候选方案。草稿可以被替换和修订，不等同于用户已确认的正式项目。

草稿包含：

- 方案摘要；
- 候选配件；
- 预算区间及其证据状态；
- 用途和外观适配说明；
- 假设与未知；
- 自动校验摘要；
- 需要用户确认的决策；
- 生成版本与来源。

### 3.3 正式方案 Build

用户接受草稿后生成的持久化方案。现有 `builds`、`build_items`、`check_runs`、`findings`、`price_evidence` 继续服务于正式方案和高级 DIY。

### 3.4 AgentRun 与 AgentEvent

一次理解、检索、生成、校验、修订或追问的运行记录。事件必须追加保存，至少包含时间、动作、状态和面向用户的短说明；失败时保留错误类别，不保存密钥或完整敏感请求。

## 4. 状态

### 4.1 设计请求状态

`received → understanding → needs_input → generating → ready_to_review → accepted / abandoned`

只有在真实歧义会改变方案时进入 `needs_input`。例如预算是否包含显示器、已有电源是否必须保留、剪辑是否优先于游戏。

### 4.2 草稿状态

`draft → validating → needs_confirmation → ready → accepted / replaced`

`needs_confirmation` 只表示用户需要做决定，不表示系统把所有技术字段都推给用户。

### 4.3 正式方案状态

保留现有 `draft / needs_confirmation / ready / checking / reviewed / stale / archived`。用户编辑后自动标记相关检查结果过期，并触发后台重新校验。

## 5. 自动化主流程

```text
接收自然语言目标
  → 结构化意图
  → 检索目录、规格、来源和价格证据
  → 生成候选组合
  → 调用兼容性规则自动校验
  → 计算已知价格与经验估算区间
  → 生成方案摘要、取舍和待确认事项
  → 用户接受、修改或进入 DIY
```

普通用户不需要先填写 CPU、主板、显卡、内存、存储、电源、散热器、机箱八类字段，也不需要手动点击“运行兼容性检查”。

## 6. Agent 职责与事实边界

### 6.1 Agent 可以做

- 理解自然语言目标；
- 判断用户是新装机、升级还是复核已有清单；
- 根据用途和预算组织候选组合；
- 检索目录、规格来源和已有价格证据；
- 解释取舍和提出少量关键追问；
- 根据用户命令修订方案；
- 组织方案和报告语言。

### 6.2 Agent 不可以单独做

- 凭经验确认精确 SKU 的所有变体；
- 生成未经依据支持的精确规格、尺寸、接口或价格；
- 把兼容性冲突说成通过；
- 自动写入用户正式项目；
- 绕过规则校验或确认门槛；
- 自动下单、支付、登录外部平台或改变用户账户。

### 6.3 来源等级

每个方案判断标记来源等级：

- `verified_catalog`：项目目录和来源记录支持；
- `user_input`：用户明确提供；
- `price_evidence`：带时间和来源的价格快照；
- `model_experience`：模型经验建议，必须标明待核实；
- `unknown`：资料不足，不能判断。

精确兼容性结论必须来自结构化事实和规则工具。模型经验可以影响取舍，不得替代事实校验。

## 7. 兼容性与前台表达

现有八类硬件和确定性规则继续保留，作为每次生成/修改后的后台护栏。

前台默认只呈现：

- 可行；
- 有一项需要确认；
- 存在冲突；
- 资料不足。

用户点“查看依据”后，才展开涉及的硬件、事实字段、规则和来源。`unknown` 仍然不能当作 `pass`，但不应把完整规则编号和字段列表压在默认页面。

发现阻断或未知时，Agent 优先提供可执行动作，例如换一件兼容硬件、补充一个关键偏好、查看依据或进入 DIY。

## 8. 预算与方案生成

预算显示区分：

- 有价格证据的已知金额；
- 只有用户输入价格的金额；
- 目录无价格时的经验估算；
- 完全未知的项目；
- 必选和可选项目。

没有可靠价格证据时，系统必须标注“经验估算”或“未知”，不能伪装为实时价格。方案可以显示预算区间，但区间来源和时间需要可查看。

方案生成优先级：

1. 满足用户明确目标；
2. 保持主要硬件兼容；
3. 控制预算；
4. 满足外观和噪音偏好；
5. 解释必要取舍；
6. 给出可接受的替代方案。

不输出无依据的综合评分，不自动替换用户已经明确保留的硬件。

## 9. 用户确认原则

只在以下情况询问：

- 多个候选会导致价格、尺寸、性能或外观明显不同；
- 用户偏好存在冲突，必须选择取舍；
- 已有硬件是否保留会改变方案；
- 关键兼容性资料不足；
- 预算口径会改变结论。

不询问：

- 可以由目录和规则安全推断的字段；
- 普通用户不需要理解的内部规则编号；
- 不影响方案方向的细小规格。

## 10. RAG 与模型策略

第一阶段不依赖向量数据库。检索上下文来自：

- 结构化硬件目录；
- 别名和型号归一化；
- 规格来源和许可证信息；
- 用户提供的输入与证据；
- 价格证据快照；
- 已确认的历史方案。

大模型使用结构化 JSON 输出，并经过 Zod 校验。模型不可用时：

- 仍可用目录候选、固定规则式方案模板和高级 DIY；
- 无法可靠理解的目标转为一句补充问题；
- 兼容性检查和报告不依赖模型；
- 不生成看似确定的假事实。

## 11. V2 第一条验收主链路

用户输入“2 万预算、白色海景房、剪辑和游戏”后，系统必须：

1. 自动提取预算、用途和外观目标；
2. 只在关键歧义时追问；
3. 生成一套可阅读、可编辑的方案草稿；
4. 自动校验主要兼容性；
5. 显示预算范围、主要取舍和待确认事项；
6. 允许用户接受、自然语言修改或进入高级 DIY；
7. 接受后生成正式 Build、检查历史和报告；
8. 模型失败时仍保留目录候选、DIY 和规则检查能力；
9. 关键建议可追溯到用户输入、目录事实、价格证据或经验标记。

## 12. 非目标

- 全网实时最低价；
- 未授权电商抓取；
- 自动下单、支付和账户操作；
- 多 Agent 角色营销；
- 无依据的性能精确预测；
- 强制用户先填写八类硬件字段；
- 用兼容性总分替代具体问题；
- 为了 Agent 形态提前引入向量数据库、消息队列或微服务。
