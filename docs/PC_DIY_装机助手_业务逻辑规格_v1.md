# PC DIY 装机助手：业务逻辑规格（V1）

> 文档状态：第一版业务规格草案  
> 版本：V1.0  
> 更新日期：2026-09-20  
> 适用范围：中国大陆市场假设下的 PC DIY 装机与升级场景  
> 技术约束：无。本文档只定义业务目标、规则、输入、输出和验收标准，不预设编程语言、前后端框架、数据库、模型供应商或 Agent 框架。

---

## 1. 文档目的

本文件是项目开始编码前的业务单一事实来源，用来回答以下问题：

- 用户到底要完成什么任务；
- 系统接收什么输入，如何判断输入是否足够；
- 哪些结论可以由确定性规则给出，哪些只能作为参考；
- 价格数据怎样表达时间、来源、渠道和可信度；
- 什么时候必须让用户确认，什么时候系统只能提示“未知”；
- V1 做什么、不做什么，以及怎样验收。

本文件**不**回答以下问题：

- 使用 Python、Java、TypeScript 还是其他语言；
- 使用单体、前后端分离、微服务还是 Serverless；
- 使用哪一种数据库、向量库、OCR 服务或大模型；
- 是否使用 LangGraph、MCP、多 Agent 或其他框架。

技术方案应在本文件稳定、样本和验收标准明确后再确定。任何技术方案都必须服从本文定义的业务行为，不能反过来为了展示技术而扩大产品范围。

## 2. 产品定义

### 2.1 暂定产品名

**PC DIY 装机助手**。

也可以在产品界面使用更易懂的描述：

> 帮助用户在购买和组装电脑前，核对配件、发现兼容性风险、查看带日期的价格证据，并在预算内比较替代方案。

### 2.2 核心用户任务

用户通常已经有以下其中一种想法：

- 我有预算，想自己选一套电脑配件；
- 我已经选了一些配件，想知道能不能装在一起；
- 我看到一个商品链接或型号，想确认是不是选对了具体版本；
- 我准备购买，但想知道当前看到的价格是否有可靠依据；
- 某个配件缺货或超预算，想找兼容的替代品；
- 我准备升级现有电脑，想知道新旧配件是否冲突。

系统的核心任务不是替用户自动购买，也不是承诺找到全网最低价，而是把一个不完整、容易出错的装机想法整理成：

1. 一份结构化的装机清单；
2. 一组已确认或待确认的具体型号；
3. 一份可复核的兼容性检查结果；
4. 一组带来源和时间的价格证据；
5. 一份预算、风险和替代方案说明；
6. 用户下一步可以执行的行动清单。

### 2.3 V1 产品判断

V1 采用以下判断：

- **DIY 是第一入口**，先服务自己选件、自己购买、自己装机或升级的用户；
- 先做“装机清单检查和决策辅助”，不做完整电商平台；
- 价格结果是“截至某个时间的参考证据”，不是实时承诺；
- 兼容性和计算结果优先由结构化数据与确定性规则产生；
- 大模型只处理适合语言理解的部分，不能凭常识代替规则；
- 对不确定的型号、价格或兼容性，系统必须明确显示不确定，不得伪装成确定结论；
- 第一版不需要多 Agent。一个受约束的任务流程已经足够，系统是否有价值由结果准确性和可复核性决定。

## 3. 目标、非目标与成功标准

### 3.1 V1 目标

V1 需要让一个 DIY 用户能够完成以下闭环：

1. 创建一份装机或升级清单；
2. 通过手动填写、粘贴型号或粘贴商品链接添加配件；
3. 将模糊名称归一化为候选的标准型号；
4. 在不确定时由用户确认具体型号或补充信息；
5. 检查核心硬件之间的基础兼容性；
6. 统计已知价格、未知价格和预算差额；
7. 查看有时间和来源的价格参考；
8. 发现阻断问题、警告和资料缺口；
9. 在必要时查看满足约束的替代方案；
10. 保存或导出一份可复核的结果。

### 3.2 V1 非目标

以下内容不属于 V1 的交付承诺：

- 全网实时最低价；
- 对所有电商平台做无授权的大规模抓取；
- 自动登录、自动领券、自动下单或自动支付；
- 价格涨跌预测或“现在不买一定涨价”的结论；
- 对二手、翻新、海外版、矿卡等复杂渠道做统一价格承诺；
- 游戏帧数、生产力性能或功耗的精确预测；
- 自动刷 BIOS、改电压、超频或执行其他高风险硬件操作；
- 电脑店报价单、截图和 PDF 的完整 OCR 体检流程；
- 显示器、键盘、鼠标、耳机等外设的全量比价；
- 操作系统、软件授权、装机服务和售后服务的独立业务；
- 用多 Agent 数量作为产品卖点；
- 让模型在没有证据时猜测具体型号、价格或兼容性。

报价单和外设可以在后续扩展，但不能为了兼容未来而污染 V1 的核心流程。

### 3.3 成功的业务定义

V1 成功不是“模型回答得像人”，而是：

- 用户能看出清单中哪些项目已确认、哪些项目仍模糊；
- 明确的兼容性冲突不会被系统漏掉或显示为通过；
- 不足以判断时，系统会显示“未知/证据不足”，而不是给出虚假的肯定；
- 每一个价格判断都可以追溯到来源、商品、渠道和采集时间；
- 用户可以根据报告决定“继续购买、补充信息、替换配件或暂停购买”；
- 用户能理解系统为什么给出某一条提醒，而不是只看到一个无法解释的总分。

## 4. 用户与典型场景

### 4.1 V1 用户分层

#### A. 新手 DIY 用户

- 有预算和用途，但对型号、接口和兼容性不熟悉；
- 需要更多解释和明确的下一步；
- 对一次错误购买的容忍度低；
- 不应被大量技术术语或不透明评分吓退。

#### B. 熟悉硬件的 DIY 玩家

- 已经有初步清单，关注型号细节、价格变化、替代方案和历史记录；
- 可能愿意修正系统的匹配结果；
- 对“只告诉我网上价格”的付费意愿未必高，因此价值应来自减少核对工作和保留决策记录。

#### C. 升级用户

- 不是从零装机，而是把新配件加入现有设备；
- 需要输入现有配件、机箱、电源和散热等信息；
- 当旧设备信息不足时，系统必须先提示缺失项，不能直接断言可升级。

### 4.2 典型触发场景

1. “我预算 8000 元，主要玩 2K 游戏，想自己买配件。”
2. “我已经选了 CPU、主板、显卡和内存，想确认能不能装。”
3. “这个商品标题很长，我不知道它对应哪个具体显卡版本。”
4. “内存和固态最近价格波动，我想保存今天看到的价格。”
5. “某个显卡缺货，给我找保持兼容的替代型号。”
6. “我想升级显卡，但不知道原来的电源和机箱能不能继续用。”

### 4.3 暂不服务的场景

- 用户只想获得一个没有任何输入约束的“最强配置”；
- 用户要求系统替自己付款或直接提交订单；
- 用户要求基于未经验证的传闻判断硬件质量；
- 用户只提供“16G 内存”“1TB 固态”这类品类级描述，却要求精确比价；
- 用户要求比较不同成色、不同渠道、不同售后条件的商品并给出一个绝对排名。

## 5. 核心概念与状态

### 5.1 核心对象

#### 装机项目（Build Project）

用户围绕一台电脑的一次装机或升级任务。至少包含：

- 项目名称；
- 使用目标；
- 预算及预算币种；
- 目标地区或配送地区；
- 配件清单；
- 检查结果；
- 价格证据；
- 最近一次检查时间。

#### 配件条目（Build Item）

清单中的一个配件需求。它可能还没有匹配到具体商品，也可能已经由用户确认。

#### 标准型号（Canonical Product）

系统用于兼容性和比较的标准化硬件型号。标准型号不能只依赖商品标题，应尽可能包含厂商、系列、型号、变体和关键规格。

#### 商品报价证据（Price Evidence）

某个标准型号在某个来源、店铺、渠道和时间点的价格观察。每一条证据是独立快照，不能被后来的价格覆盖。

#### 检查结论（Finding）

系统对一条规则、一个价格判断或一个资料缺口给出的可追溯结果。

### 5.2 项目状态

项目状态用于控制用户流程，不代表系统内部实现方式。

| 状态 | 含义 | 用户可做的事 |
|---|---|---|
| `draft` 草稿 | 已创建项目，但信息可能不完整 | 添加、修改、删除配件 |
| `needs_confirmation` 待确认 | 存在模糊型号、缺失关键字段或需要用户决定的候选项 | 确认型号、补充信息、选择候选 |
| `ready` 可检查 | 核心配件已经足以开始规则检查 | 发起检查、继续补充可选信息 |
| `checking` 检查中 | 正在生成本次检查结果 | 查看进度或等待完成 |
| `reviewed` 已有结果 | 已生成一份结果，可能包含警告或未知项 | 修正条目、重新检查、保存结果 |
| `stale` 结果过期 | 关键价格证据或规格信息已过期 | 更新价格证据或接受历史结果 |
| `archived` 已归档 | 用户不再使用该项目 | 查看历史，不参与默认检查 |

状态转换必须有原因。例如从 `reviewed` 回到 `needs_confirmation`，应说明是哪一个配件被修改或哪一项证据失效。

### 5.3 结论状态

每条检查结论只能使用以下状态之一：

- **通过（pass）**：所需字段齐全，规则成立，并且证据足够；
- **阻断（block）**：已确认存在不能接受的冲突，用户不应直接按当前清单购买；
- **警告（warn）**：可能存在风险或取舍，但不能直接判定为不可用；
- **未知（unknown）**：缺少关键数据，系统没有足够证据判断；
- **不适用（not_applicable）**：该规则对当前项目不适用。

`unknown` 不是 `pass`，也不是 `block`。在汇总中必须单独展示。

## 6. V1 用户流程

### 6.1 创建项目

用户创建项目时，系统应至少询问：

- 项目名称；
- 是全新装机还是升级；
- 预算（可暂不填写，但未填写时不能声称预算内）；
- 主要用途（例如游戏、办公、创作、开发或自定义）；
- 目标分辨率或其他目标（可选）；
- 目标地区（默认中国大陆，但应可修改）。

用途不是用来替代兼容性规则的。它只用于解释取舍、筛选替代方案和生成可选建议。

### 6.2 添加配件

V1 支持三种主要输入方式，优先级如下：

1. 手动选择类别并填写型号或关键规格；
2. 粘贴商品链接；
3. 粘贴商品标题、型号文本或多行清单。

V1 不要求通过截图或 PDF 添加 DIY 清单。截图/PDF 解析属于后续的报价单入口，不应成为 DIY 闭环的前置依赖。

每次添加后，系统应显示：

- 原始输入；
- 识别出的类别；
- 标准型号候选；
- 关键规格；
- 匹配置信度；
- 需要用户确认的字段；
- 暂时不能判断的字段。

### 6.3 型号确认

系统不得在以下情况下静默选择具体 SKU：

- 同系列存在多个长度、显存、散热、频率或接口变体；
- 商品标题缺少品牌或完整型号；
- 链接只能识别到品类，无法稳定识别标准型号；
- 同一个型号存在全新、二手、散片、海外版或不同保修渠道；
- 匹配结果只有模糊相似度，没有足够的结构化字段。

此时必须进入待确认状态，并告诉用户：

- 当前识别到的候选是什么；
- 候选之间差异是什么；
- 哪个字段会影响兼容性或价格比较；
- 用户需要补充什么信息。

### 6.4 发起检查

发起检查前，系统应先检查“前置条件”：

- 清单中是否有重复类别或缺失必需类别；
- 所有会影响兼容性的条目是否已匹配到具体型号，或已明确标记未知；
- 用户是否提供了足够的预算信息以进行预算判断；
- 价格证据是否存在；
- 项目是否是升级场景，若是，旧设备的关键配件是否已录入。

前置条件不满足时，系统可以允许用户继续，但必须明确结果会包含未知项，不能显示“已完整检查”。

### 6.5 查看结果

报告首先展示：

1. 是否存在阻断问题；
2. 有多少条警告和未知项；
3. 总预算、已知金额和未计价金额；
4. 用户最应该先处理的三件事；
5. 最近一次价格数据的日期范围。

之后按类别展示详细结论。每条结论都要能展开查看证据和规则理由。

### 6.6 修改后重新检查

用户修改型号、价格或用途后，旧结果不能继续伪装成当前结果。系统应：

- 标记受影响的结论过期；
- 保留旧结果供用户比较；
- 重新检查受影响的规则；
- 显示本次检查使用的项目版本或更新时间。

## 7. V1 硬件范围与字段

V1 核心类别为八类：

1. CPU；
2. 主板；
3. 显卡；
4. 内存；
5. SSD/HDD；
6. 电源；
7. 散热器；
8. 机箱。

### 7.1 通用字段

每个配件条目至少应支持以下字段：

- `category`：硬件类别；
- `manufacturer`：厂商；
- `series`：系列；
- `model`：型号；
- `variant`：变体描述；
- `canonical_id`：标准型号标识；
- `source_input`：用户原始输入；
- `match_status`：未匹配、候选、已确认、未知；
- `match_confidence`：匹配置信度；
- `spec_evidence`：规格来源；
- `last_verified_at`：规格最近核验时间。

### 7.2 类别关键字段

#### CPU

- 插槽；
- 核心数和线程数（可选）；
- 标称功耗或热设计信息（可选）；
- 是否为散片；
- 官方兼容主板或 BIOS 支持信息（若有可靠来源）。

#### 主板

- 插槽；
- 芯片组；
- 内存类型；
- 内存插槽数量；
- 主板板型；
- M.2/SATA 等存储接口；
- PCIe 插槽和显卡支持信息；
- BIOS/CPU 支持信息（若有可靠来源）；
- 电源接口。

#### 显卡

- GPU 系列和具体型号；
- 显存容量；
- 长度、高度、厚度或占用槽位；
- 供电接口；
- 建议电源功率（若有官方来源）；
- 全新/二手/翻新等状态。

#### 内存

- 内存代际；
- 容量；
- 单条/套装；
- 条数；
- 频率；
- 时序（可选）；
- 电压或特殊配置（可选）。

#### SSD/HDD

- 介质类型；
- 容量；
- 接口类型；
- 尺寸；
- M.2 Key 或协议（能取得时）；
- 读写规格（只作展示，不直接等同于真实体验）；
- 健康度或成色（若为二手）。

#### 电源

- 额定功率；
- 供电接口；
- 模组类型；
- 认证信息（仅作为资料展示）；
- 新旧程度和保修渠道。

#### 散热器

- 支持的 CPU 插槽；
- 散热类型；
- 散热器高度或冷排尺寸；
- 风扇和供电接口；
- 是否包含必要扣具。

#### 机箱

- 支持的主板板型；
- CPU 散热器最高高度；
- 显卡最大长度/厚度；
- 电源规格和位置；
- 风扇/冷排空间；
- 可安装硬盘类型和数量。

### 7.3 必填与可选

“必填”不是指每个商品必须知道所有字段，而是指该字段缺失时，相关规则必须输出 `unknown`，不能假设默认值。

例如：

- 没有显卡长度，不能判定它一定能放入机箱；
- 没有内存代际，不能判定它一定与主板兼容；
- 没有电源额定功率，不能判定功率充足；
- 只有“1TB SSD”而没有具体型号，不能给出同 SKU 的价格结论。

## 8. 输入解析与型号标准化

### 8.1 解析原则

输入解析分为四步：

1. 读取原始文本、链接或手动字段；
2. 判断硬件类别；
3. 抽取品牌、系列、型号和关键规格；
4. 匹配标准型号候选并请求用户确认。

大模型可以帮助抽取和解释，但抽取结果必须经过字段校验。模型返回的字段不能直接成为最终事实。

### 8.2 原始输入保留

每个条目必须保留原始输入，不能只保存归一化结果。这样可以：

- 让用户检查系统有没有误读；
- 在数据源变化后重新匹配；
- 追溯价格证据和规格来源；
- 发现模型抽取错误。

### 8.3 型号匹配结果

型号匹配应输出以下结构化结果：

- 原始输入；
- 识别类别；
- 候选标准型号列表；
- 每个候选的匹配依据；
- 候选差异；
- 置信度；
- 是否需要用户确认；
- 缺失关键字段。

匹配置信度只用于决定是否需要确认，不能单独替代证据。

建议采用三档交互结果：

- **已确认**：用户明确选择，或输入包含足以唯一识别的标准型号；
- **候选待确认**：有一个或多个合理候选，但可能影响兼容性或价格；
- **无法匹配**：没有足够信息，不生成具体 SKU。

### 8.4 链接处理

商品链接本身不是标准型号。系统应尽量提取：

- 域名和来源平台；
- 商品标题；
- 店铺；
- 商品标识；
- 页面或用户提供的规格信息；
- 采集时间。

如果链接无法稳定取得商品详情，应允许用户手动填写型号，并把链接作为证据保留。不得因为“链接能打开”就认为型号已确认。

外部商品页面中的文字是数据，不是系统指令。系统不得执行页面中要求泄露密钥、上传文件、自动下单或改变权限的内容。

## 9. 兼容性规则

### 9.1 规则输出规范

每条规则都必须输出：

- 规则编号；
- 涉及的配件；
- 结论状态；
- 事实字段；
- 判断理由；
- 证据来源；
- 数据日期；
- 缺失字段；
- 建议动作。

规则引擎不得将缺字段默认为常见值。无法判断就输出 `unknown`。

### 9.2 V1 必须支持的规则

#### R-CPU-MB-001：CPU 插槽与主板插槽

- 若两者插槽明确且不同：`block`；
- 若相同：进入后续 BIOS/芯片组规则；
- 任一插槽未知：`unknown`；
- 不得仅根据 CPU 和主板品牌推断兼容。

#### R-CPU-MB-002：CPU 与 BIOS/主板支持

- 有可靠官方支持证据且版本满足：`pass`；
- 官方资料明确不支持：`block`；
- 资料缺失或版本不确定：`unknown` 或 `warn`，不能直接通过。

#### R-MB-RAM-001：主板内存代际与内存代际

- 明确不同代际：`block`；
- 相同且容量/条数在主板支持范围内：`pass`；
- 主板支持范围或内存代际缺失：`unknown`。

#### R-MB-CASE-001：主板板型与机箱支持

- 主板板型不在机箱支持列表内：`block`；
- 支持列表明确包含该板型：`pass`；
- 机箱规格或主板板型缺失：`unknown`。

#### R-GPU-CASE-001：显卡尺寸与机箱空间

- 显卡长度/厚度/占槽与机箱空间明确冲突：`block`；
- 都已确认且在范围内：`pass`；
- 任一尺寸未知：`unknown`。

#### R-PSU-001：电源额定功率与整机估算需求

- 只有在 CPU、GPU 和其他主要部件功耗字段足够时才计算；
- 计算结果明显超过电源额定功率：`block`；
- 余量不足或功耗信息不完整：`warn` 或 `unknown`；
- 不能用“品牌好”替代额定功率和接口判断；
- 估算必须显示采用的假设和安全余量。

#### R-PSU-002：电源供电接口

- 显卡所需接口与电源已知接口明确不匹配：`block`；
- 接口都满足：`pass`；
- 接口资料缺失：`unknown`。

#### R-COOLER-001：散热器安装平台

- CPU 插槽与散热器支持插槽无交集：`block`；
- 有交集：`pass`；
- 扣具或插槽信息不完整：`unknown`。

#### R-COOLER-CASE-001：散热器高度或冷排空间

- 散热器高度超过机箱支持上限，或冷排尺寸明确冲突：`block`；
- 尺寸满足：`pass`；
- 尺寸缺失：`unknown`。

#### R-STORAGE-001：存储接口与主板支持

- SSD/HDD 接口或协议与主板不支持：`block`；
- 明确支持：`pass`；
- 主板插槽共享、协议或接口资料缺失：`unknown`。

#### R-STORAGE-002：主板存储插槽资源

- 已知设备数量超过可用插槽数量：`block`；
- 插槽数量足够：`pass`；
- 插槽共享规则未知：`unknown` 或 `warn`。

#### R-RAM-001：内存条数与通道建议

- 单条内存不是天然不兼容，但在用户选择双通道、容量规划或主板限制下可以提出 `warn`；
- 系统不得把“单条”直接判定为不能使用；
- 若用户选择的套装条数超过主板支持数量：`block`。

#### R-MB-GPU-001：显卡插槽基本可用性

- 主板没有满足显卡要求的插槽：`block`；
- 插槽满足：`pass`；
- 具体协议或资源分配可能影响性能但不影响基本安装时，输出 `warn`，不得夸大为不能使用。

### 9.3 V1 可选规则

以下规则可以在核心闭环稳定后加入：

- BIOS 版本提示的更细分；
- M.2 插槽共享导致 SATA/PCIe 端口禁用；
- 机箱风道和风扇数量建议；
- 显卡与目标分辨率的粗粒度建议；
- 内存容量与用途的建议；
- 电源效率认证与噪声信息展示。

这些规则需要足够可靠的数据，不能为了“看起来智能”而使用未经验证的常识。

### 9.4 兼容性结论的优先级

当多条规则同时存在时，按以下顺序呈现：

1. 阻断问题；
2. 会导致用户买错型号的问题；
3. 需要补充资料的未知项；
4. 影响预算或使用体验的警告；
5. 可选优化建议。

## 10. 预算与配置分析

### 10.1 价格汇总

预算汇总必须区分：

- 已确认型号且有可比较价格证据的金额；
- 已确认型号但没有有效价格证据的金额；
- 只知道品类、未确认型号的金额；
- 用户手动填写但尚未验证的金额；
- 可选配件和必需配件。

总价不能把未知项目当成零元，也不能使用模型猜测的价格填补空白。

### 10.2 预算结论

预算结论至少包含：

- 用户预算；
- 已计价金额；
- 未计价项目；
- 价格证据的时间范围；
- 预算差额或可能区间；
- 是否包含显示器、系统、外设和服务费；
- 预算结论的置信度。

如果仍有关键组件没有价格证据，只能说“当前已知部分未超预算”，不能说“整机一定在预算内”。

### 10.3 配置平衡

V1 的配置平衡只做可解释、低风险的提醒：

- 必需配件缺失；
- 目标用途与用户选择明显不一致，且有明确输入依据；
- 关键部件存在明显的预算冲突；
- 某个高价格部件的其他配套条件不足；
- 用户的目标与当前配置不匹配，但无法通过确定性规则解决。

系统不应输出一个没有解释的“配置评分”。如要评分，必须同时显示指标、权重、数据来源和适用范围，并且默认不把评分当成购买结论。

### 10.4 替代方案

替代方案必须满足以下优先级：

1. 保持与其余已确认配件兼容；
2. 保持用户选择的用途和关键目标；
3. 满足预算方向；
4. 尽量减少需要用户重新确认的字段；
5. 清楚说明性能、尺寸、保修、渠道或价格差异。

每个替代方案必须说明：

- 替代哪个条目；
- 为什么可替代；
- 保持了哪些约束；
- 改变了哪些属性；
- 使用的价格证据日期；
- 仍然未知的风险。

系统不应自动替换用户清单中的配件，必须由用户选择接受。

## 11. 价格证据模型

### 11.1 价格的定义

系统展示的不是一个脱离上下文的数字，而是一条价格证据：

> 某个具体标准型号，在某个时间、某个地区、某个平台和店铺、某种商品状态与售后条件下观察到的价格。

### 11.2 价格快照字段

每条价格快照至少包含：

- 标准型号标识；
- 商品标题；
- 平台；
- 店铺；
- 商品链接或截图等证据；
- 标价；
- 优惠后的价格；
- 优惠成立的条件；
- 运费和必要费用；
- 货币和地区；
- 全新、二手、翻新、散片等商品状态；
- 是否自营或官方渠道；
- 保修和退换货信息（能取得时）；
- 库存或可购买状态（能取得时）；
- 采集时间；
- 数据来源类型；
- 证据完整度；
- 可信度；
- 是否允许参与当前价格判断；
- 记录创建时间和修改原因。

价格快照原则上是追加写入、不可覆盖的。后来采集到的价格应成为新快照，而不是改写旧记录。

### 11.3 价格可比性

只有满足以下条件的证据才可以直接进入同一价格区间：

- 标准型号相同，或变体差异已被明确解释；
- 商品状态相同；
- 渠道和售后条件具有可比性；
- 价格口径一致，必要费用已经说明；
- 优惠条件没有被隐藏；
- 采集日期足够接近或被标记为历史参考。

以下情况不能直接混为一个“最低价”：

- 自营与第三方店铺；
- 全新与二手；
- 零售盒装与散片；
- 国行与海外版；
- 包含不同保修或服务；
- 套装商品与单件商品；
- 需要会员、地区券或绑定条件才能获得的价格。

### 11.4 新鲜度分级

默认展示分级：

- **较新**：采集时间在 24 小时内；
- **近期参考**：超过 24 小时且不超过 7 天；
- **较旧**：超过 7 天；
- **过期**：超过该品类规定的参与期限。

显卡、内存和 SSD 的价格波动可能比机箱等品类更快，因此有效期应按品类配置。上面的分级是展示基线，不是永远固定的商业事实。

过期证据可以作为历史记录展示，但不能参与“当前价格是否合理”的默认判断。

### 11.5 价格结论

价格结论至少分为：

- 证据充分，当前观察区间；
- 证据有限，仅供参考；
- 仅有较旧历史数据；
- 没有足够证据进行判断。

系统不应只显示单一最低价。更合适的输出是：

- 可比样本数量；
- 价格区间或代表值；
- 用户当前价格与区间的差异；
- 样本的日期、渠道和商品状态；
- 证据不足时的明确声明。

当找不到同一型号的可靠可比价格时，固定输出类似：

> 暂无足够证据进行当前价格判断。请确认具体型号、渠道和商品状态，或补充新的价格证据。

### 11.6 价格数据来源优先级

1. 用户主动提供的商品链接、截图、价格和采集时间；
2. 厂商官方规格和官方渠道信息；
3. 合规的电商开放平台或联盟接口；
4. 用户授权的价格记录；
5. 许可证允许使用的硬件目录或测试数据；
6. 仅用于开发测试的合成数据。

未经确认授权的大规模页面抓取不能作为产品基础。公开可访问不等于允许商用，也不等于可以长期稳定依赖。

## 12. 报告结构与表达规范

### 12.1 报告总览

报告首页应先回答：

- 当前清单是否存在明确阻断问题；
- 哪些型号还没有确认；
- 哪些规则因资料不足无法判断；
- 已知配件价格合计是多少；
- 哪些价格证据较旧；
- 用户下一步最应该做什么。

不要把所有问题压缩为一个“通过/不通过”或一个分数。

### 12.2 报告分类

报告至少包含以下分类：

1. **规格问题**：型号模糊、品牌缺失、变体不清；
2. **兼容性问题**：明确冲突、潜在风险、未知字段；
3. **价格参考**：带日期、来源、渠道和可比性说明；
4. **预算问题**：已知金额、未知金额和预算差额；
5. **配置平衡**：基于用户用途的可解释提醒；
6. **替代方案**：满足约束的候选替代；
7. **待用户确认的问题**：用户必须做出的选择。

DIY V1 不把装机费、系统安装和售后服务作为核心报告类别，但可以在项目备注中保留。

### 12.3 单条结论的六要素

每一个重要结论都必须包含：

1. **结论**：发生了什么；
2. **证据**：使用了哪些字段、来源或规则；
3. **数据日期**：规格或价格何时取得；
4. **置信度**：高、中、低，或结构化等级；
5. **假设条件**：哪些信息是用户提供、哪些信息缺失；
6. **建议动作**：用户下一步应确认、替换、更新还是可以继续。

### 12.4 语言规范

- 说明“不能判断”的原因，不要只说“系统失败”；
- 区分“不能安装”“可能影响体验”“资料不足”；
- 不使用“肯定”“绝对最低”“百分之百没问题”等无依据表述；
- 用用户能执行的动作结束每条问题；
- 价格结论必须带“截至某日”和来源；
- 不把模型生成的解释当成新的事实来源。

## 13. Agent/模型在系统中的职责边界

### 13.1 V1 推荐的流程形态

V1 采用“一个任务流程 + 多个受约束模块”的概念即可：

```text
创建/读取装机项目
    -> 解析用户输入
    -> 标准型号候选匹配
    -> 用户确认或补充信息
    -> 读取规格和价格证据
    -> 执行确定性兼容性规则
    -> 汇总预算与风险
    -> 生成可追溯报告
```

这些模块是否由一个进程、多个服务或一个 Agent 框架实现，属于后续技术决策。

### 13.2 模型适合负责的工作

- 从商品标题或用户描述中抽取候选字段；
- 把用户的自然语言目标整理成结构化偏好；
- 解释规则结果；
- 生成需要用户补充的信息；
- 根据已验证的替代候选生成对比文字；
- 将报告组织成易读的顺序。

### 13.3 模型不能单独决定的工作

- 最终标准型号；
- 兼容性通过或阻断；
- 功耗是否满足；
- 价格是否真实或当前有效；
- 是否为全网最低价；
- 是否自动替换、购买或执行外部操作。

### 13.4 多 Agent 的使用原则

V1 不为了展示“智能体”而拆分多 Agent。只有当后续出现明确需求，例如：

- 多个独立数据源需要并行查询；
- 价格查询、规则检查和替代方案搜索可以独立扩展；
- 不同模块需要不同权限、超时和重试策略；
- 任务量导致单一流程难以维护；

才考虑把模块拆成多个 Agent 或服务。拆分前必须先证明它解决了延迟、可靠性、隔离或维护问题，而不是只增加名词和调用次数。

## 14. 数据、隐私与合规边界

### 14.1 数据最小化

V1 只收集完成装机检查所必需的数据：

- 用户输入的配件和偏好；
- 项目检查结果；
- 价格和规格证据；
- 用户确认和修正记录。

不应默认收集与装机无关的个人信息，也不应把用户上传的文件或链接发送到未说明的第三方服务。

### 14.2 数据来源说明

每条外部数据都应该能说明：

- 来源；
- 获取方式；
- 获取时间；
- 使用限制；
- 是否允许持久化；
- 是否允许展示给其他用户。

开源硬件数据库只能用于其许可证允许的范围。开源目录、价格数据、零售商数据和页面抓取结果不是同一种资产，不能因为项目开源就默认可以直接商用。

### 14.3 用户贡献价格证据

如果允许用户提交价格截图或链接，系统应：

- 保存来源和提交时间；
- 标明“用户提供”而非官方验证；
- 允许其他用户看到证据等级，而不是只看到一个数字；
- 对重复、过期或明显冲突的数据进行标记；
- 在尚未核验时不把它当作高可信单一事实。

### 14.4 外部动作

V1 的外部操作以只读为主。以下行为不应自动执行：

- 自动下单或支付；
- 自动提交询价；
- 自动登录陌生平台；
- 自动修改用户账户、购物车或收货信息；
- 自动运行本地硬件控制命令。

## 15. MVP 分阶段范围

### 15.1 V1-A：可用的 DIY 清单检查

目标是验证用户是否愿意把真实装机清单交给系统检查。

包含：

- 创建项目；
- 手动录入八类硬件；
- 粘贴型号文本；
- 记录原始输入；
- 标准型号候选和用户确认；
- CPU、主板、内存、机箱、显卡、电源、散热器、存储的基础规则；
- 已知价格手动录入；
- 规则报告和未知项报告；
- 保存项目和重新检查。

不依赖实时电商接口也可以完成这一阶段。

### 15.2 V1-B：价格证据与替代方案

包含：

- 用户粘贴商品链接或价格证据；
- 价格快照追加保存；
- 新鲜度和过期标记；
- 同型号、同渠道、同成色的可比区间；
- 预算汇总；
- 基于已确认约束的替代候选；
- 报告导出或分享。

### 15.3 V1-C：真实用户验证后的增强

仅在前两个阶段有真实使用反馈后考虑：

- 合规的价格数据接入；
- 价格历史趋势；
- 收藏和价格过期提醒；
- 多套配置对比；
- 升级场景专用流程；
- 图片/截图解析；
- 电脑店报价入口；
- 更多硬件类别。

### 15.4 明确推迟的功能

- 自动购买；
- 全网最低价承诺；
- 价格预测；
- 多 Agent 宣传和复杂协作；
- 大规模爬虫；
- 全品类购物助手；
- 不可解释的配置评分。

## 16. 验收标准

### 16.1 功能验收

一份合格的 V1 至少能够：

- 新建一个全新装机项目；
- 添加八类配件中的任意条目；
- 对模糊型号显示候选或要求补充，而不是静默猜测；
- 对明确的 CPU/主板插槽冲突给出阻断；
- 对明确的内存代际冲突给出阻断；
- 对明确的显卡尺寸冲突给出阻断；
- 对明确的电源接口冲突给出阻断；
- 对缺失尺寸、功率或接口数据给出未知；
- 保存至少两条同一型号不同日期的价格快照；
- 显示价格来源、日期、渠道和商品状态；
- 过期价格不参与默认的当前判断；
- 价格证据不足时显示证据不足；
- 修改配件后让受影响的旧结果失效；
- 导出一份包含结论、证据和建议动作的报告。

### 16.2 质量验收目标

这些是初始目标，必须用真实样本校准，不是未经验证的永久承诺：

- 在人工整理的明确型号样本中，标准型号匹配准确率达到 95% 以上；
- 对有明确字段的兼容性规则，规则测试通过率达到 100%；
- 关键字段缺失时不产生“错误通过”；
- 价格快照必填字段完整率达到 95% 以上；
- 重要报告结论 100% 能追溯到规则、字段或价格证据；
- 在用户修正记录中，能够统计误匹配、误报、漏报和未知项比例；
- 至少收集 20 份脱敏的真实或用户授权装机清单作为第一轮评测样本。

“兼容性误判率”和“价格判断有用性”不能只靠模型自评，需要人工复核样本。

### 16.3 边界测试

至少覆盖：

- 同型号不同品牌或散热版本；
- 商品标题只有品类没有具体型号；
- CPU 插槽相同但 BIOS 支持未知；
- 不同内存代际；
- 单条和双条内存；
- 多个 M.2 设备与插槽共享；
- 显卡长度刚好等于机箱上限；
- 电源额定功率缺失；
- 价格优惠需要会员或优惠券；
- 全新、二手、散片混合；
- 价格证据超过有效期；
- 商品链接失效；
- 用户修改已确认型号后旧报告仍存在；
- 一条规则的数据来源互相冲突。

## 17. 评测数据与验证计划

### 17.1 数据采集顺序

1. 先找 5-10 位真实 DIY 用户访谈当前选件流程；
2. 在获得授权或脱敏后收集至少 20 份装机/升级清单；
3. 为每份清单标注正确型号、关键规格和人工兼容性结论；
4. 记录用户实际遇到的模糊描述和缺失字段；
5. 记录用户认为有帮助或没有帮助的报告内容；
6. 用这些样本建立规则测试集和型号匹配测试集。

### 17.2 需要验证的业务假设

- DIY 用户是否愿意主动录入配件，而不是只询问一句“这套行不行”；
- 用户更在意兼容性、价格证据、替代方案还是配置解释；
- 用户能否接受“当前无法判断”，还是希望系统提供更多补充入口；
- 价格快照的更新频率是否足够；
- 用户是否愿意保存和复用项目；
- 用户是否愿意为历史价格、多方案对比或详细报告付费；
- 用户提交的价格证据是否足够支持冷启动；
- 哪些字段最常缺失，哪些规则最容易产生争议。

### 17.3 不能用 Demo 代替的验证

以下内容不能仅凭一个演示视频证明：

- 市场上存在持续付费需求；
- 价格数据可以长期稳定取得；
- 模型能可靠识别中国电商商品变体；
- 多 Agent 能提高用户价值；
- 用户会长期使用价格提醒。

## 18. 商业化假设（待验证）

当前只记录假设，不把它们当成结论。

### 18.1 可能的价值路径

- 基础装机清单检查免费；
- 详细报告、历史价格和多套方案比较收费；
- 面向硬件玩家提供项目保存、分享和价格提醒；
- 后期为小型装机店提供批量清单检查或白标工具；
- 后期在有合规前提下接入联盟或导购收入。

### 18.2 信任边界

如果系统同时收取商家佣金又声称客观审查商家报价，必须公开披露利益关系。否则“价格判断是否客观”会损害产品信任。

### 18.3 V1 不先决定的事项

- 订阅还是按次收费；
- 是否接联盟佣金；
- 是否做广告；
- 是否提供商家版；
- 是否保存用户的全部历史项目。

这些事项应等用户验证和数据来源确认后再决定。

## 19. 未决问题清单

在进入正式技术设计前，需要通过用户访谈或样本确认：

1. 第一批用户是新手 DIY 用户、硬件玩家还是升级用户；
2. 默认目标地区是否只设为中国大陆；
3. V1 是否必须支持商品链接，还是先支持手动型号；
4. 价格证据由用户提供、人工录入，还是接入某个合规接口；
5. 默认价格有效期如何按品类设置；
6. 是否允许用户贡献价格证据；
7. 哪些硬件品牌和型号是首批高频目录；
8. 是否支持二手硬件，若支持，如何与全新商品隔离；
9. 升级场景是否进入 V1，还是先只做全新装机；
10. 是否需要报告导出，导出为网页、Markdown、PDF 还是其他形式；
11. 用户项目是否需要登录和跨设备保存；
12. 用户数据和价格证据的保存、删除、脱敏策略；
13. 第一阶段的收费验证方式；
14. 哪些指标达到后才允许扩展到报价单和截图入口。

未决问题没有答案时，优先选择可逆、可人工修正、数据最小化的方案，不要用复杂架构掩盖业务不确定性。

---

## 20. 后续技术设计的输入与约束

当业务样本和本文件经过一次评审后，技术设计应至少引用以下约束：

- 规则判断和价格计算必须可测试、可复核；
- 模型输出必须经过结构化校验；
- 所有外部数据都带来源和时间；
- 价格快照不可覆盖；
- 项目修改会使相关旧结论失效；
- 不能用未知数据冒充通过；
- 不能把未授权爬虫当成核心依赖；
- 高风险外部动作必须保留人工确认；
- V1 不以多 Agent 为前提；
- 技术选型必须能支持后续替换模型、价格数据源和硬件目录。

技术方案文档应回答“如何实现这些业务规则”，而不是重新讨论“要不要做全网比价”。

## 21. 术语表

| 术语 | 定义 |
|---|---|
| DIY | 用户自行选择、购买、组装或升级电脑配件的场景 |
| 标准型号 | 经过归一化、可用于规则和比较的硬件型号 |
| SKU | 具体商品或变体的识别标识，不能与泛化品类混淆 |
| 价格快照 | 某一时间对某一具体商品价格的不可覆盖记录 |
| 价格证据 | 价格快照及其来源、渠道、时间和商品状态 |
| 新鲜度 | 价格或规格数据距离采集时间的远近 |
| 可比价格 | 在型号、状态、渠道和价格口径上足够一致的价格 |
| 阻断 | 当前信息足以证明不应按当前方案继续购买或安装 |
| 警告 | 存在可能风险或取舍，但不等于确定不能使用 |
| 未知 | 缺少足够证据，系统不能判断 |
| 规则引擎 | 执行兼容性、预算和数据校验的确定性逻辑 |
| Agent | 在受约束状态和动作空间中完成任务的模型驱动流程；不是多 Agent 的同义词 |
